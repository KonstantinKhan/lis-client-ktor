# Известные проблемы

## Краткая сводка

Список известных проблем, ограничений и обходных путей.

## Критические проблемы

### 1. Ошибки авторизации через `gradlew run`

**Проблема:** При запуске через `./gradlew run` авторизация падает с ошибкой при попытке чтения пароля.

**Причина:** JVM форкается через pipe, консоли там нет — `System.console()` возвращает null.

**Обходной путь:** Используйте `./run.sh` (Linux/WSL) или `run.cmd` (Windows).

```bash
# ❌ НЕ ДЕЛАЙТЕ ТАК
./gradlew run

# ✅ ДЕЛАЙТЕ ТАК
./run.sh
```

---

### 2. Потеря изменений без `exit`

**Проблема:** Если завершить REPL без команды `exit`, изменения остаются в чекауте и не видны снаружи.

**Причина:** Это штатное поведение Loodsman — чекаут остаётся открытым.

**Обходной путь:** Всегда используйте `exit` для завершения сессии.

```bash
migration  # Миграция запущена
exit       # Делает checkin и завершает сессию
```

---

### 3. Race Condition в параллельной обработке

**Проблема:** Если модифицировать общие `MutableList` из нескольких корутин, возможны race conditions.

**Проблемный код:**
```kotlin
coroutineScope {
    dataRows.map { excelRow ->
        async {
            identifiers.add(processRow(excelRow))  // RACE CONDITION!
        }
    }.awaitAll()
}
```

**Решение:** Сливайте результаты последовательно.

```kotlin
val results = coroutineScope {
    dataRows.map { excelRow ->
        async { processRow(excelRow) }
    }.awaitAll()
}
identifiers.addAll(results)  # Безопасно
```

## Умеренные проблемы

### 4. Ошибки десериализации без `expectSuccess = true`

**Проблема:** Если `expectSuccess = false`, не-2xx ответы Loodsman доходят до `body<T>()`, который пытается десериализовать JSON ошибки как успешный DTO.

**Причина:** Loodsman отдаёт InternalServerError-style JSON на ошибках.

**Решение:** Всегда используйте `expectSuccess = true`.

```kotlin
private val client: HttpClient = HttpClient(CIO) {
    expectSuccess = true  // ✅ КРИТИЧНО ДЛЯ ОБРАБОТКИ ОШИБОК
    // ...
}
```

**Без этого:** Получаем "Illegal input: Unexpected JSON token" вместо реальной причины сбоя.

---

### 5. Memory pressure при больших Excel файлах

**Проблема:** При больших файлах (> 10k строк) может не хватить памяти.

**Причина:** 虽然 SAX-парсер используется, но результаты собираются в `List` для конкурентной обработки.

**Обходной путь:**
1. Увеличьте heap: `-Xmx4g`
2. Используйте батчинг по 1000 строк

```kotlin
dataRows.chunked(1000).forEach { batch ->
    processBatch(batch)
}
```

---

### 6. Ограничение конкурентности не распространяется на локальную работу

**Проблема:** `requestGate` ограничивает только HTTP-запросы, локальная работа (матчинг правил, сборка DTO) не контролируется.

**Причина:** Локальная работа дешёвая, контролировать её нет смысла.

**Обходной путь:** Нет необходимости, поведение штатное.

---

### 7. Атомарные счётчики не гарантируют порядок

**Проблема:** `AtomicInteger.incrementAndGet()` не гарантирует порядок увеличения.

**Причина:** Это и не требуется — счётчик нужен только для статистики.

**Обходной путь:** Нет необходимости, поведение штатное.

---

## Низкосущественные проблемы

### 8. Кэш элементов может устаревать

**Проблема:** Если элемент удаляется в Loodsman во время миграции, кэш может содержать устаревшие данные.

**Причина:** Кэш заполняется один раз при начале миграции.

**Обходной путь:** Перезапустите миграцию.

---

### 9. Логирование происходит в stdout/stderr

**Проблема:** Все логи выводятся в консоль, нет структурированного логирования.

**Причина:** Упрощение для CLI-инструмента.

**Обходной путь:** Перенаправьте вывод в файл.

```bash
./run.sh > migration.log 2>&1
```

---

### 10. Нет автоматического retry при таймаутах

**Статус:** Частично решено. Реальный инцидент — `EditObject/create-bo-object` под нагрузкой
иногда не укладывается в `requestTimeoutMillis` (30 сек), кандидат молча пропускался. Добавлен
`retryOnTransientError()` (`client/Helpers.kt`, см. [[12-key-classes.md]]) — до 3 попыток,
экспоненциальный backoff, ловит таймаут/5xx.

**Что покрыто:** `EditObject.createBoObject` и `BoReference.referenceBoVersion`
(`client/EditObject.kt`, `client/BoReference.kt`) — оба безопасны для повтора (уникальный индекс
Loodsman по `location` / идемпотентная привязка, см. [[03-external-api-quirks.md]]).

**Что НЕ покрыто (осознанно):** `EditObject.newLink`/`EditObject.create` (`new-object`) —
таймаут не гарантирует, что запрос не выполнился на сервере, повтор неидемпотентного вызова без
защиты от дубля мог бы создать второй объект/связь.

**Обходной путь для непокрытых методов:** Перезапустите миграцию.

## Ограничения

### Производительность

| Ограничение | Значение | Обходной путь |
|-------------|----------|---------------|
| Макс. конкурентных запросов | 10 (настраивается) | Измените `maxConcurrentRequests` в `settings.json` |
| Таймаут запроса | 30 секунд | Измените `requestTimeoutMillis` в `Client.kt` |
| Таймаут подключения | 10 секунд | Измените `connectTimeoutMillis` в `Client.kt` |

### Размер файлов

| Ограничение | Значение | Обходной путь |
|-------------|----------|---------------|
| Строк Excel | ~10k (без батчинга) | Используйте батчинг |
| Размер файла | ~100 MB | Увеличьте heap |
