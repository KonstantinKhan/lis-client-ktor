# Известные проблемы

## Краткая сводка

Список известных проблем, ограничений и обходных путей.

## Критические проблемы

### 1. Ошибки авторизации через `gradlew run`

**Проблема:** При запуске через `./gradlew run` авторизация падает с ошибкой при попытке чтения пароля.

**Причина:** JVM форкается через pipe, консоли там нет — `System.console()` возвращает null.

**Обходной путь:** запускайте собранный дистрибутив или fat jar напрямую, не через Gradle.

```bash
# ❌ НЕ ДЕЛАЙТЕ ТАК
./gradlew run

# ✅ ДЕЛАЙТЕ ТАК
./gradlew installDist && ./build/install/lis-client-ktor/bin/lis-client-ktor
# или
./gradlew shadowJar && java -Dfile.encoding=UTF-8 -jar build/libs/lis-client-ktor-0.0.1-all.jar
```

---

### 2. Потеря изменений без `exit`

**Проблема:** Если завершить REPL без команды `exit`, изменения остаются в чекауте и не видны снаружи.

**Причина:** Это штатное поведение Loodsman — чекаут остаётся открытым.

**Обходной путь:** Всегда используйте `exit` для завершения сессии.

```bash
migration  # Миграция запущена
exit       # Делает checkin и завершает сессию
```

---

### 3. Race Condition в параллельной обработке

**Проблема:** Если модифицировать общие `MutableList` из нескольких корутин, возможны race conditions.

**Проблемный код:**
```kotlin
coroutineScope {
    dataRows.map { excelRow ->
        async {
            identifiers.add(processRow(excelRow))  // RACE CONDITION!
        }
    }.awaitAll()
}
```

**Решение:** Сливайте результаты последовательно.

```kotlin
val results = coroutineScope {
    dataRows.map { excelRow ->
        async { processRow(excelRow) }
    }.awaitAll()
}
identifiers.addAll(results)  # Безопасно
```

## Умеренные проблемы

### 4. Ошибки десериализации без `expectSuccess = true`

**Проблема:** Если `expectSuccess = false`, не-2xx ответы Loodsman доходят до `body<T>()`, который пытается десериализовать JSON ошибки как успешный DTO.

**Причина:** Loodsman отдаёт InternalServerError-style JSON на ошибках.

**Решение:** Всегда используйте `expectSuccess = true`.

```kotlin
private val client: HttpClient = HttpClient(CIO) {
    expectSuccess = true  // ✅ КРИТИЧНО ДЛЯ ОБРАБОТКИ ОШИБОК
    // ...
}
```

**Без этого:** Получаем "Illegal input: Unexpected JSON token" вместо реальной причины сбоя.

---

### 5. Memory pressure при больших Excel файлах

**Проблема:** При больших файлах (> 10k строк) может не хватить памяти.

**Причина:** 虽然 SAX-парсер используется, но результаты собираются в `List` для конкурентной обработки.

**Обходной путь:**
1. Увеличьте heap: `-Xmx4g`
2. Используйте батчинг по 1000 строк

```kotlin
dataRows.chunked(1000).forEach { batch ->
    processBatch(batch)
}
```

---

### 6. Ограничение конкурентности не распространяется на локальную работу

**Проблема:** `requestGate` ограничивает только HTTP-запросы, локальная работа (матчинг правил, сборка DTO) не контролируется.

**Причина:** Локальная работа дешёвая, контролировать её нет смысла.

**Обходной путь:** Нет необходимости, поведение штатное.

---

### 7. Атомарные счётчики не гарантируют порядок

**Проблема:** `AtomicInteger.incrementAndGet()` не гарантирует порядок увеличения.

**Причина:** Это и не требуется — счётчик нужен только для статистики.

**Обходной путь:** Нет необходимости, поведение штатное.

---

## Низкосущественные проблемы

### 8. Кэш элементов может устаревать

**Проблема:** Если элемент удаляется в Loodsman во время миграции, кэш может содержать устаревшие данные.

**Причина:** Кэш заполняется один раз при начале миграции.

**Обходной путь:** Перезапустите миграцию.

---

### 9. Логирование происходит в stdout/stderr

**Проблема:** Все логи выводятся в консоль, нет структурированного логирования.

**Причина:** Упрощение для CLI-инструмента.

**Обходной путь:** Перенаправьте вывод в файл.

```bash
./build/install/lis-client-ktor/bin/lis-client-ktor > migration.log 2>&1
```

---

### 10. Нет автоматического retry при таймаутах

**Статус:** Частично решено. Реальный инцидент — `EditObject/create-bo-object` под нагрузкой
иногда не укладывается в `requestTimeoutMillis` (30 сек), кандидат молча пропускался. Добавлен
`retryOnTransientError()` (`client/Helpers.kt`, см. [[12-key-classes.md]]) — до `retryCount`
попыток (дефолт 3), экспоненциальный backoff от `retryDelayMillis` (дефолт 1000мс, настраиваются
в `settings.json` → `connection`, см. [[05-settings-reference.md]]), ловит таймаут/5xx.

**Что покрыто:** `EditObject.createBoObject` и `BoReference.referenceBoVersion`
(`client/EditObject.kt`, `client/BoReference.kt`) — оба безопасны для повтора (уникальный индекс
Loodsman по `location` / идемпотентная привязка, см. [[03-external-api-quirks.md]]).

**Что НЕ покрыто (осознанно):** `EditObject.newLink`/`EditObject.create` (`new-object`) —
таймаут не гарантирует, что запрос не выполнился на сервере, повтор неидемпотентного вызова без
защиты от дубля мог бы создать второй объект/связь.

**Обходной путь для непокрытых методов:** Перезапустите миграцию.

---

### 11. Протухание `access_token` ПОЛИНОМ на длинной миграции

**Статус:** Решено. Реальный инцидент — `access_token` ПОЛИНОМ живёт 600 секунд, на длинном
прогоне (большой Excel-файл) токен протухает посреди миграции, сервер начинает отвечать `401` на
ЛЮБОЙ следующий вызов ПОЛИНОМ (поиск, `getLocation`, создание элемента и т.д.).

**Фикс:** `callPolynom { token -> ... }` (`migration/PolynomAuthRetry.kt`) — ловит `401`, обновляет
токен через `PolynomLogin.updateToken` (эндпоинт был написан заранее, но не вызывался ни разу),
повторяет вызов один раз с новым токеном. Конкурентные `401` одновременно от нескольких корутин
coalesced через `MigrationContext.polynomTokenMutex` — обновляет токен только первая, остальные
переиспользуют уже обновлённое значение. Обёрнуты все 19 точек вызова `polynomClient.*` в движке.
См. [[03-external-api-quirks.md]], [[12-key-classes.md]].

### 12. `?` вместо «—» в консоли Windows (кодировка вывода)

**Проблема:** В логах вместо длинного тире печатается `?` (кириллица при этом отображается нормально).

**Причина:** Сообщения движка содержат типографское тире «—» (U+2014), а не ASCII-дефис —
например, в `MigrationEngine.kt`: «Классификация: код классификатора '...' не найден в ПОЛИНОМ —
объекты ...». Консоль Windows по умолчанию работает в OEM-кодировке CP866, где U+2014 отсутствует.
JVM при выводе в stdout кодирует строку в кодировку консоли и заменяет unmappable-символ на `?`.
Кириллица в CP866 есть — поэтому страдает только тире. В Docker (Linux) проблема не возникает.

**Обходной путь** (одна строка, PowerShell 7+ или cmd):

```powershell
chcp 65001 && java "-Dstdout.encoding=UTF-8" "-Dstderr.encoding=UTF-8" -jar build/libs/lis-client-ktor-0.0.1-all.jar
```

- `chcp 65001` — переключает текущее окно консоли на UTF-8 (действует до его закрытия);
- `-Dstdout.encoding` / `-Dstderr.encoding` (JDK 19+) — заставляют stdout/stderr писать UTF-8;
- кавычки вокруг `-D...` **обязательны** в PowerShell — его парсер спотыкается о точку в
  аргументе и разбивает `-Dstdout.encoding=UTF-8` на два токена (ошибка
  `Could not find or load main class .encoding=UTF-8`).

Альтернативы:
- `setx JAVA_TOOL_OPTIONS "-Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8"` — флаги подхватываются
  любым `java -jar` (проверка: `java -version` печатает `Picked up JAVA_TOOL_OPTIONS: ...`);
  действует только на консоли, открытые ПОСЛЕ `setx`;
- системно: галка «Бета-версия: Использовать Юникод (UTF-8) для поддержки языка во всём мире»
  (языковые настройки Windows → административные) + перезагрузка — тогда достаточно голого
  `java -jar`;
- заменить «—» на ASCII `-` в строковых литералах — работает в любой консоли без настроек.

**Нюансы:** точечные правки реестра (`HKCU\Console` CodePage, AutoRun cmd) ненадёжны — первый
игнорируется Windows Terminal, второй не действует в PowerShell. Связка «JVM пишет UTF-8 без
`chcp 65001`» даёт кракозябры (UTF-8-байты, декодируемые как CP866).

### 13. Повторный прогон шага G (сканы документов) на тех же данных

**Проблема:** find-or-create (`ObjectSearch/find-by-simple-search`) реализован только для корня
"Сканы документов". Папки объектов и сами "Бумажные документы" — нет, создаются безусловно
(`EditObject/new-object`) каждый прогон.

**Ожидаемое поведение при повторном прогоне** (следует из ограничения Loodsman "тип + ключевой
атрибут уникальны", см. [[03-external-api-quirks.md]]; отдельным вторым прогоном не
перепроверялось): попытка создать папку/документ с уже существующим ключевым атрибутом упадёт с
ошибкой API. Эта ошибка изолирована — по конструкции движка (`DocumentsEngine.kt`) она ловится
на уровне конкретной папки объекта или конкретной пары (объект, тип документа), логируется,
остальные объекты/типы того же прогона продолжают обрабатываться как обычно. То есть повторный
прогон на тех же строках не тихо плодит дубли и не роняет всю миграцию — но и не пропускает уже
загруженные документы молча, каждая уже существующая пара будет шуметь ошибкой в лог при каждом
следующем прогоне.

**Обходной путь:** держать входной Excel шага G строго добавочным (только новые строки на новый
прогон) либо вручную чистить уже загруженные строки перед повторным запуском.

**Возможное улучшение:** find-or-create по тому же паттерну, что у корня, для папки объекта и/или
для документа — не сделано осознанно в рамках этой сессии, ключевой атрибут документа
(`"<объект> - <тип>"`) для этого уже достаточно уникален.

## Ограничения

### Производительность

| Ограничение | Значение | Обходной путь |
|-------------|----------|---------------|
| Макс. конкурентных запросов | 10 (настраивается) | Измените `maxConcurrentRequests` в `settings.json` |
| Таймаут запроса | 30 секунд (настраивается) | Измените `requestTimeoutMillis` в `settings.json` |
| Таймаут подключения | 10 секунд (настраивается) | Измените `connectTimeoutMillis` в `settings.json` |

### Размер файлов

| Ограничение | Значение | Обходной путь |
|-------------|----------|---------------|
| Строк Excel | ~10k (без батчинга) | Используйте батчинг |
| Размер файла | ~100 MB | Увеличьте heap |
