# Референс `settings.json`

Про "что означает" каждое поле для бизнес-логики — [[04-business-logic.md]]. Здесь — "как
задать": какой тип, обязательное ли поле, дефолт, пример из текущего `settings.json`.

Все Kotlin-классы схемы — `@Serializable` (kotlinx.serialization), парсятся строго: поля без
дефолтного значения в Kotlin-классе обязательны в JSON. Файл читается относительно рабочей
директории (по умолчанию `settings.json`).

## Корень

```json
{ "connection": {...}, "polynom": {...}, "mapping": {...} }
```

## `connection` — подключение к Loodsman

| Поле | Тип | Дефолт | Пример |
|---|---|---|---|
| `dbName` | string | — (обязательно) | `"loodsman"` |
| `remember` | bool | `false` | `false` |
| `url` | string | — (обязательно) | `"http://127.0.0.1:8076/api/v4/"` |
| `maxConcurrentRequests` | int | `10` | `50` |

`maxConcurrentRequests` — размер `Client.requestGate: Semaphore`, единственная точка
троттлинга ко всем эндпоинтам Loodsman разом (см. [[02-external-api-principles.md]]).

## `polynom` — подключение к ПОЛИНОМ:MDM

| Поле | Тип | Дефолт | Пример |
|---|---|---|---|
| `url` | string | — (обязательно) | `"http://127.0.0.1:5100/"` |
| `storageId` | string? | `null` | `null` |
| `moduleName` | string | `"LIS-Client"` | `""` |
| `clientType` | int | `8` | `0` |
| `maxConcurrentRequests` | int | `5` | `5` |

Отдельный семафор от Loodsman — конкурентность к двум системам регулируется независимо.

## `mapping.source` — источник Excel

| Поле | Тип | Пример |
|---|---|---|
| `type` | string | `"xlsx"` (единственное поддержанное значение сейчас) |
| `path` | string | `"C:\\Users\\han\\Desktop\\data.xlsx"` |

## `mapping.objectsSheet` — лист "Объекты"

| Поле | Тип | Пример |
|---|---|---|
| `name` | string | `"Объекты"` |
| `headersRowIndex` | int (1-based!) | `1` |

`headersRowIndex` — 1-based номер строки заголовков в Excel; внутри пересчитывается в
0-based индекс автоматически.

## `mapping.linksSheet` — лист "Связи"

| Поле | Тип | Дефолт | Пример |
|---|---|---|---|
| `name` | string | — (обязательно) | `"Связи"` |
| `headersRowIndex` | int, 1-based | — (обязательно) | `1` |
| `parentColumnIndex` | int, 1-based | — (обязательно) | `1` |
| `childColumnIndex` | int, 1-based | — (обязательно) | `2` |
| `linkType` | string | `""` | `"Состоит из ..."` |
| `quantityColumn` | string | `""` | `"конструкторское количество"` |
| `unitColumn` | string | `""` | `"единица измерения входящего элемента в ДСЕ"` |
| `unitExcludeValues` | string[] | `[]` | `["шт"]` |

Отличие от `objectsSheet`: `parentColumnIndex`/`childColumnIndex` — числовые индексы столбца
(1-based), а `quantityColumn`/`unitColumn` — имена столбцов (ищутся по заголовку, не по
индексу). `quantityColumn: ""` (пусто) означает "количество всегда 1.0, столбец не читать".
`unitColumn: ""` означает "единицы измерения не резолвить вообще". `unitExcludeValues` —
значения, при которых unit конкретной связи не трогается (остаётся дефолт API), даже если
`unitColumn` в целом настроен.

## `mapping.analogGroups` — группы аналогов (лист "Связи")

| Поле | Тип | Дефолт | Пример |
|---|---|---|---|
| `analogGroupColumn` | string | `""` | `"группа аналогов"` — `""` выключает фичу целиком |
| `productionQuantityColumn` | string | `""` | `"производственное количество"` |
| `productionQuantityWithoutMergeColumn` | string | `""` | `"количество производственное без объединения"` |
| `changeGroupNameTemplate` | string | `"Группа аналогов {group}"` | `{group}` подставляется номером группы |
| `variantNameTemplate` | string | `"Вариант {variant}"` | `{variant}` подставляется номером варианта |

Формат `analogGroupColumn`: `"1-2"` = группа `1`, вариант `2` (первое число — своя группа на
родителя, второе — номер варианта внутри неё; у одного родителя может быть несколько групп).
Объект варианта — тот же потомок связи, что уже резолвится через `linksSheet.childColumnIndex`,
отдельного столбца кода классификатора не требуется.

`isBasic` варианта определяется по двум производственным столбцам: оба ≠ `0` → основной
(`isBasic=true`), оба `=0` → заменитель (`isBasic=false`), ровно одно из двух `=0` —
несогласованные данные: строка логируется и пропускается (не участвует в группе; сама
структурная связь родитель-потомок создаётся как обычно, независимо от этого правила).

Тип группы замены (`groupType`) зафиксирован в коде как `2` — тот же код, что у
`mapping.materials` (см. ниже), не вынесен в настройки.

Fallback без отдельных настроек: и поиск в ПОЛИНОМ по коду классификатора
(`classifierCodePropertyAbsoluteCode`/`classifierCodePropertyId`/`codesReferenceName`), и тип
создаваемого в Лоцман объекта (`materialTarget`) берутся напрямую из `mapping.materials` (см.
ниже) — по решению пользователя: потомок группы аналогов, не
резолвившийся в структуре, это материал-заменитель, а не отдельная сущность со своими
настройками. Создаётся через `createBoObject`/location (тем же путём, что и обычные материалы),
НЕ через обычный `EditObject/new-object` — `materialTarget` в Лоцман настроен как
ПОЛИНОМ-интегрированный тип, `new-object` для таких типов падает 500 ("Используйте метод
NewBoObject"). Обозначение объекта отдельно не задаётся — берётся автоматически из
location-привязки к найденному элементу ПОЛИНОМ (его "наименование").

## `mapping.identifierColumn`

Строка — имя столбца на листе "Объекты" с кодом классификатора объекта (используется и для
резолва листа "Связи" по коду, и как ключ идентификации строки во всех дополнительных
проверках `bomMaterials`). Пример: `"код классификатора"`.

## `mapping.attributes[]` — атрибуты объекта

Список объектов:

| Поле | Тип | Обязательное | Пример |
|---|---|---|---|
| `attrColumn` | string | да | `"наименование"` |
| `loodsmanAttr` | string | да | `"Наименование"` |
| `replace` | object? | нет | см. ниже |
| `unit` | string? | нет | `"мм"` — фиксированное обозначение единицы измерения (КОНСТАНТА из настроек, не столбец Excel), резолвится через `resolveUnitId` в `unitGuid` атрибута. `null` — атрибут без единицы. Используется в `mapping.blanks.attributes[]` (см. ниже), не используется в этом (корневом) `mapping.attributes[]` |
| `numeric` | bool | `false` | `true` — перед записью запятая в значении заменяется на точку (реальный инцидент: `ExcelSaxParser.kt` использует `DataFormatter()` без явной локали, на машине с русской локалью числовые ячейки приходят как `"0,3"`, Loodsman отвечает `410128 "Неверное значение для атрибута"` на дробные значения с запятой, см. [[03-external-api-quirks.md]]). Значение, не читающееся как число даже после замены — пропускается (лог + не проставляется). Для строковых атрибутов (Марка, ГОСТ и т.п.) оставлять `false` — запятая может быть частью текста |

`replace` — полиморфный объект (`ReplaceRule`), дискриминатор `"type"`:

```json
{ "type": "any", "find": "any", "target": "БЧ" }
```

Единственная нетривиальная реализация сейчас — `"any"`: если сырое значение непустое,
подставить `target` вместо него (используется как "флаг присутствия", не буквальный
find/replace, несмотря на названия полей `find`/`target`). Значение `find` в текущей
реализации не используется по существу.

## `mapping.types[]` — правила создания объектов

Список объектов, каждый — одно правило:

| Поле | Тип | Дефолт | Пример |
|---|---|---|---|
| `target` | string | — (обязательно) | `"Деталь"` — должен существовать как реальный тип в Loodsman (проверяется `Validator`) |
| `source` | string | — (обязательно) | `"обозначение"` — имя столбца с ключевым атрибутом |
| `state` | string? | `null` | `"Проектирование"` — обязателен по смыслу для обычного создания (`EditObject/new-object`, `stateName`), но игнорируется, если `resolveViaPolynom: true` (см. ниже) — можно не указывать в JSON |
| `isProject` | bool | `false` | `false` — см. [[03-external-api-quirks.md]] про опасность `true` |
| `isFolder` | bool | `false` | `true` для правила "Папка" |
| `linkToRoot` | bool | `false` | `true` — жёсткая привязка к root сразу после создания |
| `conditions` | `Conditions` | — (обязательно) | см. ниже |
| `childLinkType` | string? | `null` | Если задан — связь листа "Связи", где объект этого правила выступает ПОТОМКОМ, создаётся этим типом вместо `linksSheet.linkType`, И направление связи (`parentVersionId`/`childVersionId`) РАЗВОРАЧИВАЕТСЯ: субъектом связи становится сам объект-потомок, а структурный родитель листа "Связи" — объектом связи (пример — "Технологическая деталь"/"Технологическая ДСЕ для": реальный инцидент, Loodsman 500 "Нарушение правил связывания объектов" при попытке создать связь в обычном направлении — правило в Loodsman сконфигурировано только в обратную сторону). Не влияет на связь "папка→объект" и "root→объект" — только на резолв листа "Связи" |
| `childOfSameTypeLinkType` | string? | `null` | Частный случай `childLinkType`: если РОДИТЕЛЬ по листу "Связи" — тоже объект с `childLinkType` (т.е. того же "особого" класса, например тоже "Технологическая деталь"), связь создаётся этим типом вместо `childLinkType`, направление ОБЫЧНОЕ (родитель→потомок, без реверса) — как у материалов (пример: "Изготавливается из ..." для "Технологическая деталь входит в Технологическую деталь") |
| `resolveViaPolynom` | bool | `false` | Если `true` — объект правила НЕ создаётся через `EditObject/new-object`. Вместо этого код классификатора строки (`mapping.identifierColumn`) ищется в ПОЛИНОМ (тем же путём/справочником, что `mapping.materials`), и объект создаётся через `EditObject/create-bo-object` по найденному `location` (пример — "Стандартное изделие"/"Прочее изделие"). `source`/`state` правила в этом случае кодом не используются (ключевой атрибут и состояние приходят из ПОЛИНОМ/Loodsman-биндинга applicability↔state) — по решению пользователя `state` в таких правилах просто не указывается в JSON (поле опционально), а не оставляется как сбивающий с толку плейсхолдер |
| `attributes` | `Attribute[]` | `[]` | Атрибуты объекта, специфичные ТОЛЬКО для правил с этим `target` (например "Масса"←"Масса детали" настроен на всех правилах "Деталь" и "Технологическая деталь", но не на "Сборочная единица"/"Папка" и т.п.) — в ДОПОЛНЕНИЕ к глобальному `mapping.attributes[]` (оба списка объединяются, `createLoodsmanObject` в `MigrationEngine.kt`; при совпадении имени атрибута побеждает значение из этого списка). Для правила "Папка" (`isFolder: true`) атрибуты НЕ резолвятся вовсе, ни глобальные, ни свои — см. [[04-business-logic.md]]. Игнорируется при `resolveViaPolynom: true` (объект создаётся через `create-bo-object`, минуя `createLoodsmanObject`) |

### `Conditions` — условие срабатывания правила

```json
{ "single": {"type":"check","column":"...","is":"..."}, "or": [], "and": [] }
```

| Поле | Тип | Семантика |
|---|---|---|
| `single` | `Rule`? | Одно условие. `{}`/отсутствие поля `column` = не используется |
| `or` | `Rule[]` | Хотя бы одно из списка должно совпасть. `[]` = не используется |
| `and` | `Rule[]` | Все из списка должны совпасть. `[]` = не используется |

Каждая непустая (используемая) группа должна пройти — AND между группами. Пустая/
неиспользуемая группа не блокирует (считается пройденной).

### `Rule` — одно условие

| Поле | Тип | Пример |
|---|---|---|
| `type` | string | `"check"` / `"notEndsWith"` / `"empty"` — резолвится через реестр `RuleEvaluators`, список типов открыт для расширения кодом |
| `column` | string | `"Раздел спецификации"` |
| `is` | string (JSON-ключ `"is"`, в Kotlin — `isValue`) | `"Изделия"` — не нужен для `"empty"` |

Встроенные типы условий сейчас: `"check"` (точное совпадение значения), `"notEndsWith"`
(значение НЕ заканчивается на `is`), `"endsWith"` (значение заканчивается на `is`), `"empty"`
(значение отсутствует/пусто).

## `mapping.materials` — сортаментные материалы + заменители + группы замены

| Поле | Тип | Дефолт | Пример |
|---|---|---|---|
| `appliesToTargets` | string[] | — (обязательно) | `["Деталь"]` — к каким `target` из `types[]` применяется весь блок `materials` |
| `drawingDesignationColumn` | string | — (обязательно) | `"Обозначение материала по чертежу"` |
| `substituteDrawingDesignationColumn` | string | `""` | `"Материал заменитель по чертежу"` — `""` выключает поток заменителей целиком |
| `classifierCodeColumn` | string | — (обязательно) | `"Код классификатора объекта который записан в поле сортамента"` — общий и для основного материала, и для заменителя |
| `classifierCodePropertyAbsoluteCode` | string | — (обязательно) | `"c:ClassifData::pd:ClassifCode"` — код property-definition в ПОЛИНОМ, из админки |
| `codesReferenceName` | string | — (обязательно) | `"Коды"` — справочник ПОЛИНОМ для поиска по коду классификатора |
| `materialTarget` | string | — (обязательно) | `"Материал по КД"` — должен существовать как тип в Loodsman |
| `detailLinkType` | string | — (обязательно) | `"Изготавливается из ..."` — тип связи материал↔деталь (потоки A/B) |
| `hierarchy` | object | — (обязательно) | см. ниже |
| `classifierCodePropertyId` | `{objectId, typeId}`? | `null` | Прямое указание property-definition в обход резолва по `classifierCodePropertyAbsoluteCode` — на случай, если резолв по коду не сработает на конкретном экземпляре ПОЛИНОМ |
| `changeGroupName` | string | `"Замена материала"` | Название группы замены (`ObjectConfiguration/new-change-group-2`) |
| `mainMaterialVariantName` | string | `"Основной материал"` | Название варианта основного материала |
| `substituteMaterialVariantName` | string | `"Материал-заменитель"` | Название варианта заменителя |
| `attributes` | `Attribute[]` | `[]` | Атрибуты ОБЪЕКТА "Материал по КД" (например "Марка материала"←"Марка", "НТД на материал"←"ГОСТ") — та же схема `Attribute`, что у `mapping.attributes[]` (см. выше), без `unit` (не нужен для этих атрибутов). Ставятся РОВНО ОДИН раз, в момент реального создания объекта (`createBoObject`), не на каждое попадание в кэш дедупликации — см. [[04-business-logic.md]]. Пишутся через `EditObject/up-attr-value-by-id` (`assignMaterialAttributes` в `MaterialsEngine.kt`), поштучно, НЕ через `up-attr-values-by-ids` (батч, 9009 на BO-объектах) и НЕ через `up-attr-value-for-bo-by-id` ("for-bo"-вариант принимается без ошибок, но не проставляет значение) — три реальные попытки, подробности в [[03-external-api-quirks.md]] |

Тип группы замены (`groupType`) зафиксирован в коде как `2`, не вынесен в настройки — по
прямому указанию, не значение по умолчанию, которое можно было бы переопределить.

`materials.attributes` читается в ДВУХ местах: поток A/B (`MaterialsEngine.resolveOrCreateMaterial`,
столбцы читаются со строки Детали, той же, что `drawingDesignationColumn`/`classifierCodeColumn`) и
поток C (`MaterialsEngine.resolveBomMaterialByClassifierCode`, вызванный из
`runBomMaterialsMigrationInternal`, столбцы читаются со строки раздела "Материалы" на листе
"Объекты" — той, что даёт `classifierId` через `mapping.bomMaterials.materialConditions`, но сама
объект не создаёт). Оба места используют один и тот же список настроек.

### `mapping.materials.hierarchy`

Справочник → каталог → группа в ПОЛИНОМ для фолбэка "создать материал по имени", если поиск по
коду классификатора не сработал:

| Поле | Тип | Пример |
|---|---|---|
| `referenceName` | string | `"Конструкторские материалы"` |
| `catalogName` | string | `"Материалы по КД"` |
| `groupName` | string | `"Обозначение материала по чертежу"` |

Все три должны существовать в ПОЛИНОМ заранее (созданы вручную в админке) — код только
резолвит по имени, не создаёт.

## `mapping.bomMaterials` — материалы по КД для DS-объектов

| Поле | Тип | Дефолт | Пример |
|---|---|---|---|
| `specificationConditions` | `Conditions` | `Conditions()` (пусто) | признак DS на объекте |
| `materialConditions` | `Conditions` | `Conditions()` (пусто) | признак "раздел Материалы" на строке |

Обе — та же схема `Conditions`, что у `types[].conditions`, но с разной семантикой пустого
значения:

- `specificationConditions`, если не задан вовсе (пустой `Conditions()`) — **выключает весь
  поток C целиком**. Проверяется явно через служебный флаг "задано ли условие", а не через
  голый матчинг — иначе пустой `Conditions()` матчил бы вообще любую строку как DS (поведение,
  подходящее для `types[]`, но не подходящее здесь, где отсутствие настройки должно означать
  "выключено").
- `materialConditions`, если не задан — считается "всегда true" (дополнительный фильтр поверх
  `specificationConditions`, а не самостоятельный гейт; в текущей конфигурации задан явно).

Пример текущей конфигурации:

```json
"bomMaterials": {
  "specificationConditions": {
    "single": { "type": "check", "column": "конструкторская спецификация", "is": "DS" },
    "or": [], "and": []
  },
  "materialConditions": {
    "single": { "type": "check", "column": "Раздел спецификации", "is": "Материалы" },
    "or": [], "and": []
  }
}
```

Обе проверяются на строках листа "Объекты" — [[03-external-api-quirks.md]] объясняет,
почему не на "Связи" (там таких данных просто нет).

## `mapping.blanks` — заготовки и материал основной

| Поле | Тип | Дефолт | Пример |
|---|---|---|---|
| `target` | string | `""` | `"Заготовка"` — тип Loodsman создаваемой заготовки; пустое значение выключает весь поток D целиком |
| `state` | string | `""` | `"Проектирование"` — состояние заготовки (`EditObject/new-object`, `stateName`) |
| `linkType` | string | `""` | `"Заготовка для"` — тип связи деталь↔заготовка; связь РЕВЕРСИВНАЯ (субъект — заготовка, объект — деталь), см. [[04-business-logic.md]] |
| `materialTarget` | string | `""` | `"Материал основной"` — тип Loodsman создаваемого материала (BO-объект) |
| `materialLinkType` | string | `""` | `"Изготавливается из ..."` — тип связи заготовка→материал, направление обычное (заготовка субъект) |
| `rateColumn` | string | `""` | `"Норма расхода"` — столбец листа "Объекты" со значением нормы расхода; пустое значение — норма никогда не читается |
| `rateUnitColumn` | string | `""` | `"Единица измерения"` — столбец листа "Объекты" с обозначением единицы нормы |
| `rateAttribute` | string | `""` | `"Норма расхода"` — имя АТРИБУТА связи заготовка→материал в Loodsman, куда пишется норма (`EditObject/up-link-attr-values`); пустое значение — норма не проставляется |
| `appliesToTargets` | string[] | `[]` | `["Деталь", "Технологическая деталь"]` — типы Loodsman (`mappingElement.target` из `types[]`), для которых собираются кандидаты на заготовку. `[]` (дефолт) — фолбэк на `materials.appliesToTargets` (старое поведение, триггер полностью общий с потоком A). Задан явно — независимый от потока A список |
| `attributes` | `Attribute[]` | `[]` | Атрибуты ОБЪЕКТА "Заготовка" (Диаметр/Длина/Толщина и т.п., опционально с `unit`, например `"мм"`) — читаются с той же строки листа "Объекты", что и деталь. Несколько разных `attrColumn` могут указывать на один `loodsmanAttr` (например "Диаметр"/"Наружные диаметр"/"Сечение" → все в "Диаметр") — резолвленный список дедуплицируется по `loodsmanAttr` перед отправкой (побеждает последняя по порядку в списке запись), иначе дублирующееся имя атрибута в одном батче роняет `EditObject/up-attr-values-by-ids` целиком (`400`, реальный инцидент — см. [[03-external-api-quirks.md]]) |
| `materialAttributes` | `Attribute[]` | `[]` | Атрибуты СВЯЗИ `materialLinkType` ("Изготавливается из ..." заготовка → материал основной) — тот же эндпоинт `EditObject/up-link-attr-values`, что и у `rateAttribute` выше, но отдельный вызов на ту же связь (`materialLinkId`). Сюда же — атрибуты материала, которые могут отличаться между заготовками, ссылающимися на общий объект "Материал основной" (например "Профиль заготовки"), даже если в схеме Loodsman заведены на объекте: у каждой заготовки своя связь, конфликта не возникает. Реальный инцидент (`410207`, дедупликация "Материала основного") — [[03-external-api-quirks.md]] |
| `materialObjectAttributes` | `Attribute[]` | `[]` | Атрибуты ОБЪЕКТА "Материал основной" (`EditObject/up-attr-value-by-id`, тот же механизм, что `materials.attributes` у "Материала по КД") — уместны ТОЛЬКО для значений, одинаковых для любого потребителя одного физического материала: объект может быть общим на несколько заготовок (см. `materialAttributes` выше и [[03-external-api-quirks.md]]). На практике сейчас пусто — всё, что казалось атрибутом объекта, оказалось атрибутом связи |

Код классификатора (`materials.classifierCodeColumn`) НЕ дублируется отдельным полем
`blanks.*` — переиспользуется из `mapping.materials`, по решению пользователя. Целевые типы
объектов (`appliesToTargets`) — начиная с этого поля, у потока D СВОЙ список, независимый от
`materials.appliesToTargets`: это позволяет включить заготовки для типа (например
"Технологическая деталь"), не включая заодно поток A (материал по КД через ПОЛИНОМ) для того же
типа.

`rateColumn`/`rateAttribute` управляются независимо от `target`: можно включить заготовки без
нормы расхода (оставить оба поля пустыми), остальная часть потока при этом работает как обычно.
