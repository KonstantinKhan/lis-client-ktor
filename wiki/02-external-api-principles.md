# Принципы работы с внешними API

Проект интегрируется с двумя внешними системами по REST: **Loodsman PLM** (основной API,
целевая система миграции) и **ПОЛИНОМ:MDM** (справочник материалов/классификаторов,
используется только для резолва и создания материалов). У обоих — свой Ktor-клиент, свой
набор DTO, но общие архитектурные принципы. Специфичные грабли каждого API — отдельно, в
[[03-external-api-quirks.md]].

## Сборка HTTP-клиента

`client/Client.kt` (Loodsman) и `polynom/client/PolynomClient.kt` (ПОЛИНОМ) — каждый
поднимает свой `HttpClient(CIO)` с:

- `expectSuccess = true`. Это принципиально: без этого не-2xx ответы (а обе системы отдают
  на ошибках JSON-тело в духе `{"type":"...","title":"...","status":500}`) молча доходят до
  `body<T>()`, который пытается задесериализовать тело ошибки как успешный DTO — и падает с
  невнятным `"Illegal input: Unexpected JSON token"` вместо реальной причины сбоя. С
  `expectSuccess=true` не-2xx превращается в `ResponseException` с доступным
  `response.status`/`response.bodyAsText()`.
- `ContentNegotiation` с `kotlinx.serialization` (`Json { prettyPrint = true;
  encodeDefaults = true }` у Loodsman-клиента) — все DTO проекта `@Serializable`.
- `HttpTimeout` — разумные таймауты на подключение/запрос, чтобы зависший запрос не вешал
  всю миграцию бесконечно.

## Троттлинг: единственная точка — `Client.requestGate`

`Client.requestGate: Semaphore(connection.maxConcurrentRequests)` — единственная реальная
точка контроля нагрузки на Loodsman. Она оборачивает **каждый** HTTP-вызов в **каждом**
суб-клиенте (`requestGate.withPermit { ... }`), включая `Measure`/`ObjectConfiguration`,
добавленные позже основных `EditObject`/`ObjectInfo`. У ПОЛИНОМ-клиента — свой аналогичный
семафор с собственным `maxConcurrentRequests` в `settings.json.polynom`.

Локальная обработка строк Excel (матчинг условий `Conditions`, сборка DTO) — дешёвая
CPU-операция, поэтому она не троттлится отдельно: весь список строк запускается в корутинах
сразу (`rows.map { async { ... } }` внутри `coroutineScope`, `awaitAll()`), и корутины
большую часть времени просто ждут permit семафора. Троттлинг — забота семафора, не забота
кода, который его вызывает.

**Важное исключение**, обнаруженное вживую: не каждый эндпоинт Loodsman одинаково хорошо
переносит конкурентные вызовы даже под общим семафором — см.
`ObjectConfiguration/new-change-group-2` в [[03-external-api-quirks.md]].

## Сессионные заголовки

- Loodsman: `Web-Loodsman-Session: <sessionId>`, добавляется автоматически в
  `client/Helpers.kt` через `getWithSession`/`postWithSession` — обёртки над `HttpClient.get`/
  `.post`, принимающие `sessionId` явным параметром. Любой новый метод суб-клиента должен идти
  через эти хелперы, а не через голый `client.get`/`client.post`, иначе заголовок сессии не
  проставится.
- ПОЛИНОМ: bearer-токен (`polynomAccessToken` в `MigrationContext`), аналогичная обёртка —
  `polynom/client/PolynomHelpers.kt` (`postWithBearer` и т.п.).

## Паттерн нового суб-клиента / нового эндпоинта

Единообразно для обеих систем:

1. DTO запроса/ответа — `data class` с `@Serializable` в `loodsman/api/dto/` (или
   `polynom/api/dto/`), поля называются как в JSON один-в-один (snake_case не используется —
   у Loodsman/ПОЛИНОМ camelCase-поля).
2. Метод в соответствующем `client/*.kt` (или `polynom/client/*.kt`):
   ```kotlin
   suspend fun someMethod(sessionId: String, body: SomeInputDto): SomeOutputDto =
       requestGate.withPermit {
           client.postWithSession("SomeController/some-endpoint", sessionId) {
               setBody(body)
           }.body()
       }
   ```
3. Подключение в `Client.kt`/`PolynomClient.kt`: `val someClient = SomeClient(client,
   requestGate)`.

Если ответ API не задокументирован в `swagger.lapis` явно (у части эндпоинтов в
экспортированном swagger отсутствует секция `<` с типом ответа) — тип ответа устанавливается
эмпирически (обычно `IdentifierDto` — голый `Int`, обёрнутый в `@JvmInline value class`) и
проверяется первым реальным запуском; при несовпадении формы ответа сразу видна ошибка
десериализации, а не тихая порча данных.

## Паттерн конкурентной обработки

Стандартная форма по всему `migration/`:

```kotlin
val results = coroutineScope {
    items.map { item -> async { process(item) } }.awaitAll()
}
// слияние в общие изменяемые списки/множества MigrationContext — ПОСЛЕ awaitAll(),
// последовательно, а не из корутин напрямую (иначе гонка на MutableList/MutableSet)
```

Ключевые правила:

- Источник данных (строки Excel) собирается **полностью** в `List` до начала конкурентной
обработки (`ExcelSaxParser.parse(...).toList()`) — см. антипаттерн `flatMapMerge` в
[[03-external-api-quirks.md]] за тем, почему это не опционально.
- Резолв "по уникальному значению, не по каждой записи" — там, где значение часто
  повторяется (единица измерения, код классификатора материала), сначала собирается
  `Set` уникальных значений, резолвится конкурентно один раз на значение, и только потом
  результат раздаётся всем записям через `Map`. Экономит повторные одинаковые HTTP-вызовы.
- Дедупликация "какой ресурс создать один раз, даже если к нему пришло несколько параллельных
  кандидатов" — через общий `MutableMap` + `Mutex` (`elementCache`/`elementCacheMutex` в
  `MaterialsEngine.kt`): без него конкурентные корутины могут одновременно не найти
  существующий ресурс и обе попытаться создать новый, что либо дублирует данные, либо падает
  на уникальном индексе БД.

## Обработка ошибок

- Ktor `ResponseException` — стандартный способ ошибки при `expectSuccess=true`.
  `e.response.bodyAsText()` — `suspend`-вызов, поэтому его нельзя вызвать внутри
  синхронного `except {}` COR-воркера напрямую; паттерн проекта — обернуть содержательный
  вызов в собственный `try/catch (e: ResponseException)` внутри самой `suspend`-функции
  (`runMaterialsMigration`, `runBomMaterialsMigration`), напечатать статус+тело там, где это
  ещё возможно, и перебросить исключение дальше — `except {}` worker'а тогда просто печатает
  `e.message` и тоже перебрасывает.
- Внутри одной "пачки" обработки (строка Excel, кандидат на материал, конкурентная связь)
  — `try/catch (e: Exception)` вокруг конкретного HTTP-вызова, инкремент счётчика ошибок,
  `System.err.println` с деталями (что именно не удалось и с каким id/кодом), **не** проброс
  исключения дальше — единичная неудача не должна остановить обработку остальных 400 строк.

## Философия "пропустить + залогировать + посчитать" vs "упасть"

Проект последовательно разделяет два класса проблем:

- **Ожидаемые, частые в реальных данных ситуации** — не ошибка всей миграции: не найдено
  соответствие в ПОЛИНОМ по коду классификатора, коллизия обозначения единицы измерения
  между разными величинами, деталь без собственного обозначения по чертежу, нерезолвленная
  связь. Реакция везде одна: `AtomicInteger`-счётчик + `println`/`System.err.println` с
  деталями (id/код, чтобы можно было найти конкретную строку в Excel) + обработка
  продолжается. Итоговая строка `println` в конце каждого шага суммирует все счётчики разом.
- **Данные/конфигурация, без которых миграция в принципе не может быть корректной** — падение
  всего процесса: `target`-тип из `settings.json`, отсутствующий в Loodsman
  (`Validator.isValidTarget`); справочник/каталог/группа в ПОЛИНОМ, не найденные по имени
  (`resolveMaterialsGroup`/`resolveSearchScope` — `throw IllegalStateException` с явным
  указанием, что нужно завести вручную). Здесь молчаливое "пропустить" замаскировало бы
  системную проблему конфигурации под видом единичных пропусков.
