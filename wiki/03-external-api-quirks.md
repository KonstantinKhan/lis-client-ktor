# Особенности внешних API (наработано вживую)

Всё в этом документе установлено эмпирически — реальными запусками против боевого/тестового
стенда Loodsman и ПОЛИНОМ, часто ценой нескольких часов отладки. Источник, где не указано
иное — `swagger.lapis` (корень репозитория) + ручная проверка через Swagger UI/логи ошибок
реального сервера.

## Loodsman: объекты и чекаут

- **`EditObject/new-object` создаёт объект сразу в текущем подключённом чекауте** —
  подтверждено вручную через Swagger. Отдельный эндпоинт `insert-object`
  (`InsertObjectModel`, есть в `loodsman/api/dto/` как наследие старого экспериментального
  кода в `Main.kt`) для базового сценария создания не нужен.
- **Содержимое чекаута не видно снаружи текущей сессии** — ни в UI-списке "объекты за
  сегодня", ни в других сессиях под тем же логином — до `CheckOut/check-in-2` (команда `exit`
  → `LoodsmanExit` → `workers/CheckoutWorkers.kt:checkin()`). Это штатное поведение Loodsman,
  не повод искать баг, если созданные объекты "не видны" сразу после `migration`.
- **Чекаут открывается ИМЕННО на созданном root-объекте** — `checkout()` в
  `workers/CheckoutWorkers.kt` вызывается с `typeName`/`name` только что созданного root'а,
  сразу после `createRoot()`, до `connectCheckout()`. Вся структура миграции создаётся уже
  внутри этого чекаута — отдельно "брать в работу" ничего не нужно.
- **`isProject=true` делает объект отдельным ПРОЕКТОМ верхнего уровня** в клиенте Loodsman —
  он будет отображаться на одном уровне с другими проектами независимо от структурных связей
  (`newLink`). Использовать `isProject=true` только для настоящего корня миграции ("Миграция",
  создаётся в `workers/CreateWorkers.kt:createRoot()`). Реальный инцидент: если поставить
  `isProject=true` на промежуточную папку проекта — она "задвоится": будет и вложена по
  структуре, и торчать отдельным проектом рядом с root. Исправлено переводом
  `"Папка".isProject` в `false` в `settings.json`.
- **`newLink`/`create`/`createBoObject` возвращают `IdentifierDto`** — голый `Int`
  (`@JvmInline value class`), не задокументированный явно в swagger.lapis для этих
  эндпоинтов — установлено эмпирически (первый запуск падал бы с ошибкой десериализации,
  если бы форма ответа отличалась). Для `new-link` этот `Int` — `idLink` только что созданной
  связи (то же значение, что отдаёт `idLink` в `ObjectInfo/get-linked-fast`) — нужен, если дальше
  требуется что-то сделать именно со связью (например `up-link-attr-values`, см. ниже), а не с
  объектами на её концах.
- **Атрибуты связи — отдельный эндпоинт от атрибутов объекта и от встроенного количества.**
  Три разных механизма, которые легко перепутать:
  1. `EditObject/up-attr-values-by-ids` (`UpAttrValuesByIdsInputDto{versionId, attributeName,
     attributeValue, unitGuid}`) — атрибут ОБЪЕКТА, `versionId` — id объекта.
  2. `NewLinkInputDto.minQuantity`/`maxQuantity`/`unitId` (при создании связи) — встроенное
     количество/единица САМОЙ связи (величина состава BOM), не атрибут в общем смысле, отдельного
     эндпоинта для правки после создания нет (только `EditObject/up-link`, см. ниже).
  3. `EditObject/up-link-attr-values` (`UpLinkAttrValuesInputDto{linkId, attributeName,
     attributeValue, unitGuid}`) — произвольный КАСТОМНЫЙ атрибут СВЯЗИ (заведённый в схеме
     Loodsman, например величина "Масса" для "Нормы расхода"), `linkId` — id связи (`idLink`),
     НЕ id объекта. Реальный инцидент: норма расхода изначально по ошибке проставлялась через
     механизм (2) (`minQuantity`/`maxQuantity`/`unitId`) — оставалась пустой, потому что это два
     независимых механизма в схеме Loodsman, один не подставляется за другой. Правильный путь —
     (3), с `linkId`, полученным из возврата `new-link` (см. пункт выше). Подробности —
     [[04-business-logic.md]] (поток D, заготовки), [[11-api-reference.md]].
     **Второй реальный инцидент того же рода**: атрибут "Цех-потребитель" (потоки E/F, литейные
     заготовки/вспомогательные материалы) изначально по ошибке реализован через механизм (1)
     (`up-attr-values-by-ids` по `versionId` материала) — Loodsman отвечал `410202 "Атрибут не
     соответствует типу"`, потому что в схеме атрибут заведён именно на связи "Состоит из ...",
     не на объекте. Фикс — тот же путь (3), `up-link-attr-values` по `linkId` связи
     комплект→материал. Ошибка `410202` в общем случае означает именно это — атрибут в вызове
     привязан не к тому носителю (объект vs связь) в схеме Loodsman.
- **`EditObject/up-attr-values-by-ids` (батч) падает `400 "Входной набор данных не уникален"`,
  если в одном вызове дважды встречается пара (`versionId`, `attributeName`)** — Loodsman не
  разрешает дублирующиеся записи внутри одного батча, вся отправка целиком отклоняется (не
  "последняя запись побеждает", как можно было бы ожидать). Реальный инцидент: атрибуты объекта
  "Заготовка" (`blanks.attributes`) — несколько разных `attrColumn` мапятся на один и тот же
  `loodsmanAttr` (например "1-я стенка" и "Высота" оба → "Высота", под разные формы заготовки).
  Предполагалось, что на реальных данных заполнен только один столбец из такой группы на строку —
  оказалось, не всегда: на части строк заполнены ОБА, оба резолвились в отдельные записи с
  ОДИНАКОВЫМ `attributeName` в одном батче → 400 → падал ВЕСЬ кандидат целиком (заготовка/материал/
  связи для этой строки не создавались вовсе, не только сам атрибут). Фикс —
  `AttributeResolver.resolveAttributesWithUnits()` дедуплицирует результат по `loodsmanAttr`
  ПЕРЕД отправкой (`associateBy`, последняя по порядку в списке настроек запись побеждает), см.
  [[04-business-logic.md]] (поток D, п.5).
- **Атрибуты объекта, интегрированного с ПОЛИНОМ:MDM (BO-объект, создан через `create-bo-object`),
  нельзя ставить через `EditObject/up-attr-values-by-ids`** — Loodsman отвечает `9009 "Метод
  AddAttrValues неприменим для обновления интегрированных с ПОЛИНОМ:MDM атрибутов. Используйте
  методы UpAttrValueForBo или UpAttrValueForBoById"`. Реальный инцидент, ТРИ попытки, прежде чем
  нашёлся рабочий вариант:
  1. `setValues`/`up-attr-values-by-ids` (батч, как обычные атрибуты объекта в
     `createLoodsmanObject`, `MigrationEngine.kt`) — падает с 9009 на BO-объектах.
  2. Батчевый `EditObject/update-attribute-values-for-bo` (`UpdateAttributeValuesForBoInputDto`,
     ответ с полем `errorCode`) — вызывался без единой ошибки, но результата не давал (значение
     оставалось пустым в Loodsman). Судя по всему, это отдельный метод не под ту область
     атрибутов, что имела в виду ошибка 9009 (рядом в `swagger.lapis` — семейство
     `set-independent-attributes`/"независимые атрибуты", другая концепция схемы Loodsman).
  3. `EditObject/up-attr-value-for-bo-by-id` (`UpAttrValueForBoByIdInputDto{idVersion, attrName,
     attrValue, idUnit, delete, bindingRuleId, location}`) — буквальное совпадение со вторым
     методом, названным в тексте ошибки 9009 (`UpAttrValueForBoById`). Тоже принимался без ошибок
     (200, пустое тело ответа — сам эндпоинт без документированного тела в `swagger.lapis`, тот же
     приём, что `EditObject/up-link`), тоже БЕЗ эффекта — подтверждено проверкой ПОСЛЕ `exit`
     (check-in), не вопрос видимости чекаута.

  **Рабочий вариант**, найденный вручную через Swagger UI (`curl` напрямую на
  `EditObject/up-attr-value-by-id`) — обычный ПОШТУЧНЫЙ (не батч) `EditObject/up-attr-value-by-id`
  (`UpAttrValueByIdInputDto{idVersion, attrName, attrValue, idUnit, delete}`, БЕЗ `location`/
  `bindingRuleId`) — та же операция, что `up-attr-values-by-ids` (батч), но, судя по всему, без
  встроенной проверки на ПОЛИНОМ-интеграцию, которая блокирует именно батчевый метод. Рабочая
  несостыковка/баг на стороне самого Loodsman (batch-метод проверяет и блокирует, поштучный —
  нет), не в клиенте. Реализация — `MaterialsEngine.assignMaterialAttributes()`
  (`EditObject.upAttrValueById`, по одному вызову на атрибут). Та же функция переиспользуется для
  `blanks.materialObjectAttributes` ("Материал основной", если там когда-нибудь понадобится
  атрибут ОБЪЕКТА) — но см. следующий пункт: на практике для "Материала основного" почти всегда
  нужен атрибут СВЯЗИ, не объекта, по отдельной причине.
- **`410207 "Нет правила для создания атрибута связи"` — атрибут связи не привязан к этому типу
  связи в схеме Loodsman.** Реальный инцидент, атрибут "Профиль заготовки"/"Форма сортамента"
  (`blanks.materialAttributes`, связь "Изготавливается из ..." заготовка → материал основной),
  три шага:
  1. Изначально настроен как атрибут СВЯЗИ (`materialAttributes`) с именем "Форма сортамента" —
     Loodsman отвечал `410207`: в схеме атрибут "Форма сортамента" не привязан к типу связи
     "Изготавливается из ..." правилом (`ConfMetaData/add-link-attr`), в отличие от соседнего
     "Единица нормирования материала" (та же связь, тот же вызов `setLinkAttrValues`, но у неё
     правило привязки в схеме есть — поэтому она проставлялась без проблем).
  2. Гипотеза (неверная, но правдоподобная): раз "Единица нормирования материала" — атрибут
     связи и работает, а "Форма сортамента" — нет, значит "Форма сортамента" на самом деле
     атрибут ОБЪЕКТА "Материал основной" — перенесено в `blanks.materialObjectAttributes`,
     `410207` действительно пропал (вызов `up-attr-value-by-id` в обход `410207`, тот же
     инцидент выше). Но эта гипотеза вскрыла ОТДЕЛЬНУЮ, более серьёзную проблему — см. следующий
     пункт.
  3. Настоящий фикс — НЕ "объект вместо связи", а новый, отдельно заведённый в Loodsman
     link-атрибут "Профиль заготовки" (с правилом привязки к нужному типу связи), и
     `blanks.materialAttributes` указывает на него (`attrColumn: "Профиль заготовки",
     loodsmanAttr: "Профиль заготовки"`), а не на старый непривязанный "Форма сортамента".
     Атрибут связи оказался и правильным семантически (см. следующий пункт), просто под старым
     именем не имел нужного правила привязки в схеме.
- **"Материал основной" может быть ОДНИМ объектом на НЕСКОЛЬКО заготовок** — если у Детали и её
  Технологической детали (или у нескольких Деталей) совпадает код классификатора материала, они
  резолвятся в один и тот же ПОЛИНОМ `location`, а значит и в один и тот же Loodsman BO-объект
  (см. уникальный индекс на `location` ниже, в разделе ПОЛИНОМ:MDM — создать второй объект на тот
  же `location` физически нельзя, это не опциональное поведение клиента). Реальный инцидент: пока
  "Форма сортамента" была настроена как атрибут ОБЪЕКТА "Материала основного" (шаг 2 выше), на паре
  кандидатов с общим материалом выигрывало значение того, кто обработался первым (порядок корутин
  не гарантирован), второй кандидат видел чужое значение. Правило на будущее: атрибут материала —
  атрибут ОБЪЕКТА (`blanks.materialObjectAttributes`) уместен, только если значение гарантированно
  одинаково для ЛЮБОГО потребителя одного физического материала; всё, что может отличаться между
  заготовками (форма/профиль конкретного отреза и т.п.) — атрибут СВЯЗИ (`blanks.materialAttributes`):
  связь у каждого кандидата своя, даже когда материал общий, конфликта не возникает. Подробности
  потока — [[04-business-logic.md]] (поток D).
- **Числовые атрибуты Excel-ячеек могут прийти с запятой вместо точки** — `ExcelSaxParser.kt`
  строит `DataFormatter()` без явной локали, значит числовое значение форматируется через
  `Locale.getDefault()` JVM-процесса; на машине с русской локалью (типичный случай — миграция
  запускается на Windows с ru-RU) ячейка `0.3` приходит в код как строка `"0,3"`. Loodsman
  отвечает `410128 "Неверное значение для атрибута"` на числовой атрибут со значением через
  запятую (или, для некоторых типов атрибутов, значение просто остаётся непроставленным без явной
  ошибки). Тот же класс проблемы уже был известен для `blanks.rateColumn`/`linksSheet.quantityColumn`
  (оба явно делают `.replace(",", ".")` перед `toDoubleOrNull()`) — для универсального механизма
  атрибутов (`mapping.attributes[]`/`materials.attributes`/`blanks.attributes`/
  `blanks.materialAttributes`) добавлен флаг `Attribute.numeric` (см.
  [[05-settings-reference.md]]): при `numeric: true` `AttributeResolver.normalizeIfNumeric()`
  заменяет запятую на точку перед отправкой в Loodsman; значение, не читающееся как число даже
  после замены — пропускается (лог, атрибут не проставляется), а не блокирует остальные атрибуты
  строки.
- **`EditObject/up-link` — метод POST, а не PUT.** Первоначальный дизайн-документ
  (`docs/link-measure-unit-migration.md`, написан до сверки со `swagger.lapis`) утверждал PUT;
  реальный `swagger.lapis` (`create_up_link POST /api/v4/EditObject/up-link`) говорит POST.
  Swagger — источник истины, метод реализован как POST через уже существующий
  `postWithSession`, без отдельного `putWithSession`-хелпера.
- **`up-link`: `delLink` обязательно `false` явно** — если не передать `false` (или передать
  `true`), связь удаляется, а не обновляется. `EditObject.upLink` в коде построен, но пока не
  вызывается из движка миграции (см. [[04-business-logic.md]], "осознанно не сделано").

## Конкурентность: что подтверждено рабочим, а что — нет

- **Подтверждено рабочим**: конкурентные запросы на создание объектов/связей
  (`new-object`/`new-link`) в рамках одного чекаута Loodsman переносит нормально — проверено
  на `maxConcurrentRequests: 10` и ~400 строках, 0 потерянных объектов.
- **Реальный инцидент, НЕ подтверждено рабочим**:
  `ObjectConfiguration/new-change-group-2` не безопасен для конкурентных вызовов даже на
  РАЗНЫЕ объекты. Конкурентный запуск (несколько деталей параллельно, каждая — свой
  `versionId`) уронил PostgreSQL в deadlock:
  ```
  40P01: deadlock detected
  Where: while locking tuple (0,28) in relation "stchanges"
  PL/pgSQL function dt_variants.prnewchangegroup(...)
    -> dt_access.objectallowupdate -> dt_access.slgobjectallowupdate
    -> dt_access.checklock (lock на stlocks/stchanges)
  ```
  Причина — внутри хранимой процедуры Loodsman на стороне Postgres какая-то блокировка не
  построчно-независима (в отличие от процедур `new-object`/`new-link`). Исправление на
  стороне клиента: `MaterialsEngine.createSubstituteChangeGroups` вызывает создание группы
  замены **последовательно** (`forEach`, без `async`/`awaitAll`), а не конкурентно. Деталей с
  заменителем материала в реальных данных обычно немного, так что сериализация здесь не
  бутылочное горлышко. Если когда-нибудь понадобится ускорить этот шаг — сначала
  воспроизвести отсутствие deadlock'а на реальном стенде, а не полагаться на предположение,
  что проблема была в чём-то другом.
- **Антипаттерн, вызвавший другой реальный deadlock** (не гипотетический, воспроизведён):
  `flatMapMerge` поверх `channelFlow`, который блокирующе (`trySendBlocking`) кормит данные из
  чужого Java SAX-парсера (POI/Xerces), да ещё с ранней отменой через `.first{}` — вызвало
  зависание на ~400 строках (объекты переставали создаваться после первого, без единой ошибки
  в логе, зависание на много минут). Кооперативная отмена корутин через `trySendBlocking` не
  гарантированно долетает сквозь произвольный чужой blocking-код, который может проглотить
  `CancellationException` как обычный `RuntimeException`. Рабочее решение:
  `ExcelSaxParser.parse()` собирается ПОЛНОСТЬЮ в `List` через `.toList()` (без ранней
  отмены), и только потом список обрабатывается конкурентно через `async`/`awaitAll`.

## Loodsman: единицы измерения (`Measure`)

- `Measure/units-by-designation` может вернуть **0 или больше 1** результата на одно
  обозначение. Обозначение единицы (например "шт") может быть неуникальным между разными
  величинами (Measure) — коллизия. Оба случая (не найдено / коллизия) обрабатываются
  одинаково: unit для соответствующих связей не проставляется, случай логируется и считается
  отдельными счётчиками (`unitsNotFound`/`unitsCollision`), миграция продолжается — это не
  ошибка, а открытый вопрос данных, требующий ручного решения (см. `docs/
  link-measure-unit-migration.md`, раздел "Открытые вопросы").
- В API нет отдельного поля для прямой установки `idMeasure` на связи — `Measure` выводится
  сервером из выбранного `Unit` (каждый `Unit` принадлежит ровно одной `Measure`). Чтобы
  поменять величину связи, меняется `unitId`.
- `MetaData/get-measure-list-for-link` — опциональный safety-check ("подтвердить, что
  величина, пришедшая с Unit, вообще допустима для пары типов + типа связи"), описан в
  дизайн-документе, но НЕ реализован — сознательно отложено, не блокирует основной поток.
- **Реальный инцидент, тай-брейк по величине**: обозначение "г" одновременно существует в двух
  РАЗНЫХ величинах — "Масса" и "Год" — что раньше считалось коллизией (2 совпадения,
  `unitsCollision`), unit не проставлялся вовсе, Loodsman молча подставлял дефолтный юнит величины
  ("кг"). `resolveUnitId` (`MigrationEngine.kt`) получил опциональный параметр
  `preferredMeasureName` — НЕ фильтр (нельзя резать совпадения по величине заранее: то же
  обозначение может быть валидным для СОВСЕМ других атрибутов, например "м2"/"м3" для норм расхода
  других материалов), а тай-брейк: применяется, только если designation реально неоднозначен (>1
  совпадения) — если среди совпадений ровно одно с предпочтительной величиной, берётся оно; если
  совпадений одно и без того, тай-брейк не учитывается вовсе. `BlanksEngine.kt`/
  `CastingBlanksEngine.kt`/`AuxMaterialsEngine.kt` передают `"Масса"` для норм расхода (величина
  атрибута "Норма расхода" в схеме Loodsman фиксирована), остальные вызовы (единица измерения
  листа "Связи", материалы по КД) тай-брейк не передают — величина там заранее не известна.

## ПОЛИНОМ:MDM

- **Резолв property-definition по коду классификатора** — из трёх опробованных путей
  рабочим оказался только один:
  - `concept/get-all` — виснет насмерть (не используется).
  - `concept-property-source/get-by-code` — требует концепт (concept) в запросе и всё равно
    даёт 404 даже с верным концептом.
  - `concept-property-source/get-by-id` — 404 даже на id, полученный из соседнего эндпоинта
    того же понятия (`get-property-sources`).
  - **Рабочий путь**: `concept-property-source/get-by-absolute-code` — один прямой запрос по
    полному коду (`absoluteCode`, берётся из админки ПОЛИНОМ напрямую), без concept-скоупа и
    без предварительного поиска понятия/бутстрапа.
- **`ownerScope` в `search/execute-property-search`** — это не справочник/папка, а ПОНЯТИЕ
  (concept) в терминах ПОЛИНОМ. Без scope (`null`) сервер падает с 500 `NullReferenceException`.
  Найти правильное понятие ("Элемент классификации") можно тем же рабочим путём, что и для
  бутстрапа property-definition — `concept/get-by-concept-appointer` на первую группу каталога
  справочника "Коды" (этот эндпоинт всегда работал, ломались только code/id-résolв свойств).
- **Справочники/каталоги/группы ПОЛИНОМ создаются вручную в админке**, не программно. Правила
  связывания типов между Loodsman и ПОЛИНОМ настраиваются вручную и **не подхватывают**
  объекты, созданные программно через API — реальный инцидент с `pdmErrorCode 501` при
  попытке создать такую структуру через API. Код (`resolveMaterialsGroup`/
  `resolveSearchScope` в `MaterialsEngine.kt`) поэтому только резолвит существующую
  структуру по имени и явно падает с понятным сообщением, если чего-то не хватает — не
  пытается создать недостающее сам.
- Уникальный индекс на стороне Loodsman (`idx_uq_stmain_stkeyattr_inidtype`, код ошибки
  Postgres `23505`) — если `createBoObject` вызвать дважды с одинаковым `location`
  (одинаковый элемент ПОЛИНОМ), второй вызов падает. Отсюда обязательность кэша
  "элемент ПОЛИНОМ → уже созданный Loodsman-объект" везде, где несколько кандидатов могут
  резолвиться в один и тот же элемент (см. [[02-external-api-principles.md]]).
- **`access_token` живёт 600 секунд — реальный инцидент на длинной миграции**: под нагрузкой на
  большом Excel-файле токен протухает посреди прогона, сервер начинает отвечать `401` на ЛЮБОЙ
  следующий вызов ПОЛИНОМ (поиск, получение location, создание элемента и т.д. — не только на
  каком-то одном эндпоинте). Фикс — `callPolynom { token -> ... }` (`migration/PolynomAuthRetry.kt`):
  оборачивает один вызов, ловит `ResponseException` со статусом `401`, обновляет токен через
  `PolynomLogin.updateToken(accessToken, refreshToken)` (эндпоинт `api/v1/login/update-token`,
  ранее был написан, но не вызывался ни разу), повторяет вызов РОВНО один раз с новым токеном.
  Конкурентные вызовы, поймавшие `401` одновременно (типичный случай — токен протух, и все
  запросы "в полёте" в этот момент 401-ятся разом), coalesced через `MigrationContext.
  polynomTokenMutex`: под локом сверяется, не обновил ли токен уже кто-то другой, пока текущая
  корутина ждала — если да, используется уже обновлённое значение без второго сетевого запроса на
  обновление. Обёрнуты ВСЕ 19 точек вызова `polynomClient.*` в движке (`MigrationEngine.kt`,
  `MaterialsEngine.kt`, `AnalogGroupsEngine.kt`) — не выборочно, поскольку любой из них может
  оказаться первым вызовом после истечения токена. `updateToken` вызывается со СТАРЫМ (уже
  протухшим) `accessToken` в Bearer-заголовке — так спроектирован сам эндпоинт ПОЛИНОМ (принимает
  протухший, но валидно подписанный токен вместе с `refresh_token`), это не баг клиента.
- **`BoReference/reference-bo-version` — отдельный метод для привязки УЖЕ существующей версии
  Loodsman к элементу ПОЛИНОМ** (`ReferenceBOVersionInputDto{versionId, boTypeBindingRuleId,
  objectLocation}`), в отличие от `create-bo-object`, который создаёт объект и привязывает его
  за один вызов. Нужен именно для объектов, изначально созданных обычным `EditObject/new-object`
  (без интеграции с ПОЛИНОМ на момент создания) — см. классификацию объектов в
  [[04-business-logic.md]]. `boTypeBindingRuleId` в проекте зафиксирован в `0` (не вынесен в
  настройки, аналогично `CHANGE_GROUP_TYPE_MATERIAL` для групп замены). Объекты, уже созданные
  через `create-bo-object`, повторно через `reference-bo-version` не проводятся — привязка у них
  уже есть.

## Реальный инцидент: таймаут `create-bo-object` под нагрузкой + retry

`EditObject/create-bo-object` на боевом прогоне иногда не укладывается в `requestTimeoutMillis`
(30 секунд) — `Request timeout has expired [url=.../EditObject/create-bo-object,
request_timeout=30000 ms]`. Без повтора кандидат молча пропускается (штатный fallback уже
логирует и продолжает — не падение миграции, но недосозданный объект без ручного вмешательства).

Фикс — `retryOnTransientError()` (`client/Helpers.kt`): до 3 попыток, экспоненциальный backoff
(1с → 2с), ловит только `HttpRequestTimeoutException` и `ResponseException` с 5xx-статусом.
Обёрнуты **только** `EditObject.createBoObject` и `BoReference.referenceBoVersion` — retry
находится СНАРУЖИ `requestGate.withPermit` (не держит permit семафора на время задержки между
попытками).

**Осознанно не применён к `new-object`/`new-link`** — таймаут не гарантирует, что запрос не
выполнился на сервере, только что ответ не долетел; повтор неидемпотентного вызова без защиты от
дубля может создать второй объект/связь с теми же данными. `create-bo-object` безопасен для
retry именно благодаря уникальному индексу по `location` (см. пункт выше) — повтор после
реально успешного первого вызова упадёт на конфликте индекса, а не создаст тихий дубль.
`reference-bo-version` идемпотентен по своей природе — повторная привязка того же `versionId` к
тому же `location` не создаёт новых сущностей.

## Известные ограничения текущей реализации

Явно НЕ сделано, со ссылкой на то, где это могло бы понадобиться:

  `gradlew run`/в CI — только через `installDist`-бинарник, запущенный из настоящего
  терминала.
