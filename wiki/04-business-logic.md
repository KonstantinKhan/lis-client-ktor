# Текущая бизнес-логика

Что миграция реально делает с данными, шаг за шагом — со ссылками на технические детали, но
без ухода в код. Термины расшифрованы в `raw/06-glossary.md`; поля `settings.json` — в
`raw/05-settings-reference.md`.

## Шаг 1. Объекты (лист "Объекты")

Каждая строка листа "Объекты" проверяется против списка правил `mapping.types[]`. Правило —
это условие (`Conditions`) + какой тип Loodsman создавать + из какого столбца брать ключевой
атрибут + состояние + признак папки/проекта/привязки к root.

- **Одна строка может совпасть с несколькими правилами одновременно.** Типичный пример:
  строка с "Раздел спецификации" = "Изделия" совпадает и с правилом "Папка" (организационный
  контейнер), и с правилом "Сборочная единица" (реальный объект структуры) — для обеих строка
  задаёт одно и то же обозначение. В этом случае создаются ОБА объекта.
- Если среди совпавших правил есть папка — все НЕ-папочные объекты той же строки
  автоматически линкуются к этой папке (а не к root). Папка при этом не участвует в
  дальнейшей структуре BOM (не попадает в резолв листа "Связи") — иначе её код классификатора
  коллизировал бы с кодом настоящего объекта той же строки.
- Строки, которые НЕ совпали ни с одним правилом `types[]` (типичный случай — раздел
  "Материалы": для него нет типового правила), не создают объект вообще. Но их код
  классификатора всё равно может быть собран для двух отдельных целей ниже: кандидаты на
  сортаментный материал и признак "строка раздела Материалы" для DS-потока.

## Шаг 2. Связи (лист "Связи")

Каждая строка листа "Связи" — пара (родитель, потомок) по коду классификатора + опционально
количество и обозначение единицы измерения. Для каждой пары ищутся уже созданные на шаге 1
объекты с таким кодом классификатора, и между ними создаётся связь `Состоит из ...`
(настраиваемый тип связи).

- **Количество**: если колонка настроена, но конкретное значение не читается — пара
  пропускается целиком (не линкуется с дефолтом "1"), это осознанное решение: молчаливая
  подстановка неверного количества хуже отсутствующей связи.
- **Единица измерения**: опциональна. Если задан столбец с обозначением единицы (например
  "шт", "м2") — оно резолвится через ПОЛИНОМ/Loodsman `Measure/units-by-designation` в
  идентификатор единицы и передаётся при создании связи. Значения из настраиваемого списка
  исключений (например "-", "компл") — unit для них никогда не резолвится, остаётся дефолт
  API. Резолв идёт по уникальным обозначениям один раз (не по каждой связи отдельно) — одно и
  то же обозначение обычно повторяется в сотнях строк.
- Если пара по коду классификатора не резолвится ни в один объект — по умолчанию связь
  теряется (это нормально: часть строк листа "Связи" может ссылаться на данные, которых нет
  на листе "Объекты", например справочные материалы). Исключение — DS-поток, см. ниже.

## Материалы — три независимых потока

Проект поддерживает три разных источника материалов, каждый со своей логикой резолва/создания
и своим типом связи с родителем.

### Поток A: сортаментные материалы (через ПОЛИНОМ, по деталям)

Для объектов целевого типа (обычно "Деталь") на листе "Объекты" читаются два столбца:
обозначение материала по чертежу и код классификатора материала (в поле "сортамент" — не
путать с кодом классификатора самой детали). Дальше:

1. Поиск элемента в ПОЛИНОМ по коду классификатора. Если найден — его наименование
   сравнивается с обозначением по чертежу. Совпало — материал резолвлен.
2. Если код пуст, не нашёл совпадения или обозначения не совпали — фолбэк: поиск/создание
   элемента в справочнике ПОЛИНОМ "Материалы по КД" ПО ИМЕНИ (по самому обозначению).
3. Если и обозначения по чертежу тоже нет — материал не создаётся для этой детали вообще (не
   ошибка — деталям с неполными данными просто не с чем сопоставлять).

Дедупликация: детали с одинаковым кодом классификатора материала группируются, резолв идёт
ОДИН раз на группу (по представителю группы с непустым обозначением). Но линковка — только к
тем деталям группы, у которых СВОЁ обозначение по чертежу непустое: деталь без своего
обозначения не получает материал, даже если код совпал с другой деталью группы и материал
через неё успешно резолвился — так решил владелец продукта, чтобы не приписывать материал
деталям по случайному совпадению кода.

Найденный/созданный элемент ПОЛИНОМ материализуется в Loodsman через `createBoObject`
(единый нативный вызов "создать объект и связать с элементом ПОЛИНОМ по location-строке").
Связь с деталью — настраиваемый тип (по умолчанию "Изготавливается из ...").

### Поток B: материалы-заменители

Второй, полностью независимый кандидат материала на ту же деталь — из отдельного столбца
"обозначение заменителя". Разделяет с основным материалом всё остальное: тот же код
классификатора (в этом проекте у заменителя нет отдельной колонки кода), тот же справочник
ПОЛИНОМ, тот же тип связи с деталью. Собирается в ОТДЕЛЬНЫЙ список кандидатов, не смешивается
с основными: если бы основной материал и заменитель одной детали (с общим кодом
классификатора) попали в одну группу дедупликации, схлопнулись бы в один резолв, и связался
бы только один из двух. Ячейка с обозначением заменителя должна быть реально заполнена — иначе
кандидат для этой детали не создаётся вовсе (не пытается резолвиться "в пустоту").

### Поток C: материалы по КД для DS-объектов (по коду классификатора, без ПОЛИНОМ-фолбэка)

Отдельный сценарий, ортогональный к потокам A/B: объект (обычно сборочная единица) может
иметь признак "у меня есть собственная конструкторская спецификация" (условно "DS"). Для
таких объектов на листе "Связи" могут встречаться потомки, которых НЕТ среди объектов,
созданных на шаге 1 — потому что на листе "Объекты" эти потомки соответствуют строкам раздела
"Материалы", для которого нет типового правила `types[]` (см. шаг 1).

Логика: если родитель отмечен DS **и** потомок по коду классификатора — это строка раздела
"Материалы" (проверяется на самом листе "Объекты", НЕ на "Связи" — на "Связи" раздела
спецификации просто нет как данных, см. `raw/03-external-api-quirks.md`), то код
классификатора потомка ищется в ПОЛИНОМ. В отличие от потока A:

- **Нет сравнения обозначения** — обозначения по чертежу для этой строки просто нет, сравнивать
  не с чем.
- **Нет фолбэка на создание нового элемента в ПОЛИНОМ** — если код не нашёл совпадения, связь
  для этой пары просто не создаётся (лог + счётчик, не ошибка).
- **Связь — тем же типом, что обычный BOM** ("Состоит из ..."), НЕ типом "Изготавливается из
  ...", как в потоках A/B — материал по КД здесь встроен прямо в структуру состава изделия, а
  не привязан отдельным атрибутным линком к детали.
- Количество и единица измерения этой связи читаются с ТОЙ ЖЕ строки листа "Связи", что и для
  обычных BOM-связей — реальный инцидент: изначально эти поля не собирались вовсе, и все связи
  через этот поток создавались с дефолтом API (количество 1, без единицы измерения), никак не
  выделяясь среди корректно заполненных связей.

## Группы замены материала

Финальный, самый специфичный шаг — только для деталей, у которых успешно резолвились И
основной материал (поток A), И заменитель (поток B). Цель — сделать в Loodsman формальную
"группу замены" с двумя вариантами (основной/заменитель), а не просто две независимые связи
"Изготавливается из ...".

На деталь:

1. Создать группу замены (тип группы — фиксированный код "материал", задан напрямую, не
   вынесен в настройки).
2. Один запрос получить обе уже созданные связи "Изготавливается из ..." этой детали (основной
   материал + заменитель находятся под одним родителем — не нужно два отдельных запроса).
3. Сопоставить каждую связь с нужной стороной (основной/заменитель) по точному
   идентификатору созданного материала — не по названию/версии, так надёжнее, раз оба
   идентификатора уже точно известны.
4. Создать два варианта замены внутри группы: основной (флаг "базовый" = true) и заменитель
   (флаг "базовый" = false), с настраиваемыми названиями вариантов.

Если хотя бы одна из двух связей не находится на шаге 2 — вся группа для этой детали
пропускается с логом (не создаётся наполовину, с одним вариантом).

**Важно про конкурентность**: этот шаг выполняется строго последовательно по деталям (не
параллельно) — см. `raw/03-external-api-quirks.md`, реальный deadlock на стороне Postgres при
попытке распараллелить.

## Группы аналогов (лист "Связи")

Независимая от групп замены материала (выше) фича — тот же API-механизм (`ObjectConfiguration/
new-change-group-2` + `new-change-variant-2`, тот же жёсткий `groupType=2`), но источник данных
и уровень другой: не пара основной/заменитель материала одной детали, а произвольное множество
детей одного родителя (обычно сборки), объединённых значением столбца "группа аналогов" листа
"Связи".

Формат "группа аналогов": `"1-2"` — первое число - номер группы замены (свой на родителя, у
одного родителя может быть несколько групп с разными номерами), второе - номер варианта внутри
группы. Объект варианта - потомок этой же строки "Связи" (тот же объект, что уже резолвится
обычной структурной связью родитель-потомок, отдельного столбца кода классификатора не
требуется).

`isBasic` варианта определяется по двум столбцам "производственное количество" и "количество
производственное без объединения": оба значения не равны `0` - основной вариант
(`isBasic=true`), оба равны `0` - заменитель (`isBasic=false`). Если равно `0` только одно из
двух - это ошибка исходных данных: логируется, строка не участвует в группе аналогов (но её
обычная структурная связь родитель-потомок создаётся как всегда, независимо).

Обработка (`AnalogGroupsEngine.runAnalogGroupsMigration`) идёт сразу после того, как в рамках
шага "Связи" реально созданы все структурные связи - `idLink`, нужный для
`new-change-variant-2`, существует только у уже созданной связи (`ObjectInfo/get-linked-fast`
по родителю, один запрос закрывает все варианты его группы разом). Кандидаты группируются по
паре (родитель, номер группы); если хотя бы один вариант группы не резолвится в `idLink` -
группа пропускается целиком (не создаётся частично), лог + счётчик.

**Конкурентность**: как и у групп замены материала, обработка идёт строго последовательно по
группам (не параллельно) - тот же документированный deadlock Postgres при конкурентных вызовах
`new-change-group-2` (см. `raw/03-external-api-quirks.md`).

**Fallback: потомок не создан на шаге "Объекты", но есть в ПОЛИНОМ.** Реальный инцидент: часть
потомков из "код классификатора входящего объекта" (тот же столбец, что структурная связь
родитель-потомок) не резолвится ни в один объект, реально созданный на шаге "Объекты" -
типичная причина, как и у "Материалы по КД для DS" (поток C): строка раздела "Материалы", для
которого нет типового правила `types[]`. Раньше такая связь молча терялась. Теперь, если строка
дополнительно относится к группе аналогов, код классификатора потомка ищется в ПОЛИНОМ (те же
`classifierCodeProperty`/`searchScope`, что у `mapping.materials` - решение пользователя не
дублировать настройку под отдельный смысл "код классификатора"), и если найден - объект
создаётся В ЛОЦМАН через `createBoObject`/location (тот же путь, что у материалов -
`resolveOrCreateMaterial`/`resolveBomMaterialByClassifierCode` в `MaterialsEngine.kt`), НЕ через
обычный `EditObject/new-object`: реальный инцидент, `new-object` падает 500 "Метод NewObject
неприменим для создания интегрированных с ПОЛИНОМ:MDM объектов. Используйте метод NewBoObject" -
`materials.materialTarget` ("Материал по КД") в этом экземпляре Лоцман настроен как
ПОЛИНОМ-интегрированный тип. Тип - `mapping.materials.materialTarget` (состояние `create-bo-object`
не принимает вовсе - его резолвит сам Лоцман через привязку типа к свойству "применяемость"
ПОЛИНОМ, настроенную в админке; отдельного `materialState` в схеме больше нет - было мёртвым
полем, нигде не читалось кодом)
(это материал-заменитель по смыслу, отдельных настроек нет - более ранний реальный инцидент: с
типом "Деталь" группа замены у Лоцман отображалась только с одним вариантом). Обозначение
объекту отдельно не задаётся - оно автоматически берётся из location-привязки к найденному
элементу ПОЛИНОМ (его "наименование"), как и у обычных материалов. Дальше для него создаётся
обычная структурная связь с родителем (количество/единица - с той же строки "Связи")
и он участвует в построении группы аналогов как обычно. Если код классификатора не находится и
в ПОЛИНОМ - лог + пропуск, без фолбэка на создание нового элемента классификатора (в отличие от
потока A/сортаментных материалов).

**Приоритет над потоком C (материалы по КД для DS).** Пара родитель-потомок может ОДНОВРЕМЕННО
подходить под условия потока C (родитель - DS, потомок - строка раздела "Материалы") И быть
частью группы аналогов. Реальный инцидент: раньше эти две ветки проверялись как взаимоисключающие
(`else if`) в порядке "сначала DS/поток C, потом группа аналогов" - при пересечении условий пара
уходила в поток C, группа аналогов молча теряла этот вариант, а поток C создавал бы объект ещё
раз отдельным вызовом (конфликт по уникальному индексу location). Порядок проверки перевёрнут:
группа аналогов (более специфичный сигнал - явно указан в данных) проверяется ПЕРВОЙ, поток C -
только если группы аналогов нет.

Вызывается напрямую из конца шага "Связи" (`runLinksMigration`), а не отдельным шагом
пайплайна - в отличие от материалов по КД для DS-объектов, здесь не нужен отдельный проход по
ПОЛИНОМ, только Loodsman над уже полностью резолвленными в рамках шага "Связи" данными.

## Технологические детали (лист "Объекты", `types[].childLinkType`)

Четыре комбинации условий на лист "Объекты" (все — "Раздел спецификации"="Детали"):
"Тип объекта"=пусто + "Тип АСУП"="дет" + обозначение оканчивается на "Т"/"T"; "Тип
объекта"="Образец" + "Тип АСУП"="дет"; "Тип объекта"="Образец" + "Тип АСУП"="литье"; "Тип
объекта"="Заготовка" + "Тип АСУП"="литье" — раньше не совпадали ни с одним правилом `types[]`
(правило "Деталь" явно требует "Тип объекта" пусто И обозначение НЕ оканчивается на "Т"/"T") и
поэтому не создавали объект вообще, как и раздел "Материалы".

Теперь для этих 4 комбинаций отдельными правилами `types[]` создаётся объект типа
"Технологическая деталь". Единственное отличие от обычного правила — `childLinkType`
("Технологическая ДСЕ для"): когда этот объект резолвится как ПОТОМОК на листе "Связи" (по тому
же коду классификатора, что и обычный BOM), связь создаётся этим типом вместо
`linksSheet.linkType` ("Состоит из ..."), И В ОБРАТНОМ НАПРАВЛЕНИИ — субъектом связи
(`parentVersionId`) становится сама "Технологическая деталь", а структурный родитель листа
"Связи" — объектом связи (`childVersionId`). Реальный инцидент: правило связывания в Loodsman
для типа "Технологическая ДСЕ для" сконфигурировано только в этом направлении; попытка создать
связь как обычно (родитель листа "Связи" → потомок) падает 500 "Нарушение правил связывания
объектов: [Деталь] [Технологическая ДСЕ для] [Технологическая деталь]". Количество/единица
измерения при этом всё равно берутся с той же строки листа "Связи", что и для обычного BOM —
меняется только направление и тип самой связи, не источник количества.

**Частный случай: "Технологическая деталь" входит в "Технологическую деталь".** Если на листе
"Связи" родитель пары САМ является объектом с `childLinkType` (т.е. тоже создан одним из этих 4
правил), это уже не структурная ДСЕ-связь — тип связи `childOfSameTypeLinkType`
("Изготавливается из ..."), направление ОБЫЧНОЕ (родитель→потомок, БЕЗ реверса), как у
материалов. Условие определяется исключительно наличием `childLinkType` у родителя — отдельного
сравнения `target`-строк не требуется, поскольку сегодня `childLinkType` выставлен только на
правилах "Технологическая деталь".

Технически: `childLinkType`/`childOfSameTypeLinkType` хранятся на `MappingElement` и
переносятся на `Identifier` созданного объекта в момент его регистрации для резолва листа
"Связи" — поэтому для каждой конкретной строки решение "каким типом и в какую сторону линковать"
известно уже на этапе "Объекты", до всякого резолва пар родитель/потомок; сам выбор типа/
направления — в точке вызова `linkObjects` в `runLinksMigration` (`MigrationEngine.kt`). Правило
`"endsWith"` (реестр `RuleEvaluators`) — новый тип условия, зеркальный уже существовавшему
`"notEndsWith"`.

## Стандартные и Прочие изделия (лист "Объекты", `types[].resolveViaPolynom`)

Три комбинации условий (все — "Тип объекта"=пусто): "Раздел спецификации"="Стандартные
изделия" + "Тип АСУП"="дет" ИЛИ "Тип АСУП"="покуп" → **"Стандартное изделие"**; "Раздел спецификации"="Прочие
изделия" + "Тип АСУП"="покуп" → **"Прочее изделие"**. Как и с технологическими деталями, раньше
такие строки не совпадали ни с одним правилом `types[]` и не создавали объект вообще.

В отличие от технологических деталей (обычный `EditObject/new-object`), эти объекты создаются
ТЕМ ЖЕ путём, что материалы по КД и fallback групп аналогов: код классификатора строки
(`mapping.identifierColumn`) ищется в ПОЛИНОМ (общий с `mapping.materials` справочник "Коды" —
по решению пользователя отдельной настройки нет), и найденный элемент материализуется в
Loodsman через `EditObject/create-bo-object` по `location`, без сравнения обозначений (в отличие
от `resolveOrCreateMaterial`, здесь без сверки "обозначение" ↔ имя элемента ПОЛИНОМ — как в
`AnalogGroupsEngine`'s fallback). Если код не находится в ПОЛИНОМ — лог + пропуск, объект для
строки не создаётся (не ошибка).

Состояние (`state`) объекту клиент не проставляет — `EditObject/create-bo-object` вообще не
принимает поле состояния. Loodsman резолвит состояние сам через уже существующую (для "Материал
по КД") привязку типа к свойству "применяемость" ПОЛИНОМ, настроенную в админке Loodsman
(`ExternalObjects/add-bo-state-and-type-state`) — по решению пользователя, тот же механизм нужно
настроить и для этих двух новых типов, административно, не кодом. `source`/`state` этих правил
`types[]` кодом не используются (плейсхолдеры для валидности схемы).

Технически, в отличие от технологических деталей, эти объекты не создаются сразу в
`processObjectRow` — правила с `resolveViaPolynom=true` откладываются в
`PolynomBackedObjectCandidate(classifierId, target)`, а резолвятся одним батчем
(`resolvePolynomBackedObjects`) в конце `runObjectsMigration()`, ПОСЛЕ того как все строки листа
"Объекты" уже прочитаны, но ДО того как этот шаг пайплайна завершится — созданные `Identifier`
добавляются в общий список до старта `runLinksMigration()`, поэтому резолв связей/количества/
единицы измерения для них ничем не отличается от обычных объектов (`linksSheet.linkType`,
без реверса). Дедупликация — `groupBy` по коду классификатора (один resolve-вызов на уникальный
код), без отдельного кэша/мьютекса, тот же приём, что у
`AnalogGroupsEngine.resolveUnresolvedAnalogGroupCandidates`. Переиспользуются public-хелперы
`resolveSearchScope()`/`resolvePropertyDefinitionByAbsoluteCode(...)` (`MaterialsEngine.kt`).

## Порядок шагов и почему именно такой

`Объекты → Связи → Материалы (A+B+группы замены) → Материалы по КД для DS (C)`. Материалы
идут строго после связей, потому что поток C зависит от того, какие связи резолвились/не
резолвились на шаге "Связи" (нерезолвленные пары под DS-родителями — это и есть кандидаты
потока C). Группы замены идут внутри шага "Материалы", после того как оба списка кандидатов
(основной + заменитель) уже обработаны и известно, для каких деталей резолвилось и то, и
другое.
