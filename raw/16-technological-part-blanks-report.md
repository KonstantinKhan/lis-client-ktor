# Отчёт: заготовка для "Технологической детали" (независимый триггер потока D)

Итоговый отчёт по правке потока D (`mapping.blanks`) — раньше заготовки создавались только для
типов из `materials.appliesToTargets` (общий триггер с потоком A). Не входит в `wiki/index.md` —
сырой отчёт для истории, актуальная выжимка перенесена в `wiki/04-business-logic.md`,
`wiki/05-settings-reference.md`.

## Постановка задачи

Нужно было включить создание "Заготовки" (и привязанного "Материала основного") ещё и для
"Технологическая деталь" — по аналогии с уже работающим потоком для "Деталь". Условие
пользователя: поток A ("Материал по КД" через ПОЛИНОМ, связь "Изготавливается из ...") для
"Технологическая деталь" включать **не нужно** — только заготовки.

## Почему одной правки `settings.json` не хватило

Разбор кода (`MigrationEngine.kt`, `processObjectRow`) показал: до этой правки поток D читал
кандидатов из ТОГО ЖЕ списка `materialTargetObjects`, что и поток A — оба были отфильтрованы
по единственному списку `mapping.materials.appliesToTargets`. Осознанное прежнее решение (см.
комментарий в `BlanksSettings.kt`): "не дублировать конфиг под тот же смысл".

Следствие: добавление `"Технологическая деталь"` в `materials.appliesToTargets` включило бы
поток A и поток D разом — задаче не соответствует (поток A для технологической детали должен
остаться выключенным). Нужен отдельный список таргетов для потока D — это уже правка кода.

## Что сделано

1. **`domain/BlanksSettings.kt`** — новое поле:
   ```kotlin
   val appliesToTargets: List<String> = emptyList()
   ```
   Пусто (дефолт) — обратная совместимость, фолбэк на `materials.appliesToTargets` (старое
   поведение для существующих конфигов не меняется). Задан явно — независимый от потока A
   список таргетов для заготовок.

2. **`migration/MigrationEngine.kt`** (`processObjectRow`) — введён отдельный
   `blankTargetObjects`, посчитанный по `blanks.appliesToTargets.ifEmpty { materials.appliesToTargets }`,
   используется вместо `materialTargetObjects` при сборе `blankCandidatesForRow`.
   `materialTargetObjects`/поток A/поток B — без изменений, продолжают фильтроваться только по
   `materials.appliesToTargets`.

3. **`settings.json`** — `mapping.blanks.appliesToTargets = ["Деталь", "Технологическая
   деталь"]`. `mapping.materials.appliesToTargets` оставлен `["Деталь"]` без изменений — поток A
   для технологической детали по-прежнему выключен.

Остальная часть пути заготовок (`BlanksEngine.kt`) изменений не потребовала — она уже полностью
generic, не содержит хардкода типа "Деталь", работает с любым типом-родителем кандидата.

## Риск, не относящийся к коду клиента

Реверсивная связь `blanks.linkType` ("Заготовка для", субъект — заготовка, объект — деталь)
должна быть настроена в самом Loodsman (админка) как допустимая для пары
(Заготовка → Технологическая деталь) — так же, как уже настроена для пары
(Заготовка → Деталь). Если правило связывания в Loodsman не расширено на новую пару типов, будет
`500 "Нарушение правил связывания объектов"` при первом запуске (тот же класс инцидента, что уже
был с "Технологическая ДСЕ для" — см. `wiki/03-external-api-quirks.md`). Настраивается
администратором Loodsman, не в этом репозитории. На момент отчёта — пользователь подтвердил, что
билд собирается и фича работает.

## Изменённые файлы

- `migration/MigrationEngine.kt` — `blankTargetObjects`, независимый от `materialTargetObjects`
- `settings.json` — `mapping.blanks.appliesToTargets`
