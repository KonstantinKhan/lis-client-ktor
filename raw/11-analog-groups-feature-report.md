# Отчёт: группы аналогов (лист "Связи")

Итоговый отчёт по реализации новой фичи — групп замены "аналог", формируемых из данных листа
"Связи" обменного файла. Фиксирует бизнес-правила, изменённые/новые файлы и инциденты, найденные
и исправленные в ходе отладки на реальных данных.

## Что сделано

На листе "Связи" читаются новые столбцы: `производственное количество`, `количество
производственное без объединения` (оба Double-строкой) и `группа аналогов` (формат `"1-1"`,
`"1-2"` и т.д.). На их основе для родителя строится в Loodsman формальная "группа замены" —
тот же API-механизм (`ObjectConfiguration/new-change-group-2` + `new-change-variant-2`), что уже
использовался для групп замены материала, но здесь группа объединяет произвольное множество
потомков одного родителя, а не пару основной/заменитель материала одной детали.

### Правила

1. `группа аналогов` непусто → первая цифра — номер группы замены (свой на родителя, у одного
   родителя может быть несколько групп), вторая цифра — номер варианта. Объект варианта — тот же
   потомок связи, что уже резолвится через `linksSheet.childColumnIndex` ("код классификатора
   входящего объекта") — отдельного столбца кода не потребовалось.
2. Оба производственных количества ≠ `0` → основной вариант (`isBasic=true`). Оба `=0` →
   заменитель (`isBasic=false`). Ровно одно из двух `=0` — ошибка данных: лог + пропуск строки
   (не участвует в группе; обычная структурная связь родитель-потомок создаётся как всегда).
3. `группа аналогов` пусто → строка вне логики групп аналогов.
4. `groupType` для `new-change-group-2` — тот же жёсткий код `2`, что и у групп замены материала.

### Fallback: потомок не создан на шаге "Объекты", но есть в ПОЛИНОМ

Реальный сценарий: часть потомков из "группы аналогов" — строки раздела "Материалы", для
которого нет типового правила `mapping.types[]`, поэтому на шаге "Объекты" для них не создаётся
Loodsman-объект. Раньше такая связь молча терялась. Теперь, если код классификатора потомка
находится в ПОЛИНОМ, объект создаётся в Loodsman через `createBoObject`/location (тем же путём,
что и обычные материалы), после чего создаётся обычная структурная связь с родителем и потомок
участвует в построении группы аналогов как обычно. Тип/состояние — переиспользуют
`mapping.materials.materialTarget`/`materialState` (это материал-заменитель по смыслу, отдельных
настроек не заводили). Если код классификатора не находится и в ПОЛИНОМ — лог + пропуск, без
фолбэка на создание нового элемента классификатора.

## Новые настройки (`mapping.analogGroups`)

```json
"analogGroups": {
  "analogGroupColumn": "группа аналогов",
  "productionQuantityColumn": "производственное количество",
  "productionQuantityWithoutMergeColumn": "количество производственное без объединения",
  "changeGroupNameTemplate": "Группа аналогов {group}",
  "variantNameTemplate": "Вариант {variant}"
}
```

Отдельных `fallbackObjectTarget`/`fallbackObjectState` нет — намеренно, см. инцидент №2 ниже.

## Изменённые/новые файлы

- `domain/AnalogGroupCandidate.kt`, `domain/UnresolvedAnalogGroupCandidate.kt` — новые
- `domain/AnalogGroupsSettings.kt` — новый
- `domain/MigrationContext.kt` — новые поля `analogGroupCandidates`/`unresolvedAnalogGroupCandidates`
- `mapping/Mapping.kt` — новое поле `analogGroups`
- `migration/AnalogGroupResolver.kt` — парсинг `"1-2"` и производственных количеств
- `migration/AnalogGroupsEngine.kt` — построение групп/вариантов, fallback-резолв через ПОЛИНОМ
- `migration/MigrationEngine.kt` — чтение новых столбцов в `runLinksMigration`, сбор кандидатов,
  вызов `runAnalogGroupsMigration()` в конце шага "Связи"
- `migration/MaterialsEngine.kt` — `resolveSearchScope`/`resolvePropertyDefinitionByAbsoluteCode`
  распривачены для переиспользования из `AnalogGroupsEngine.kt`
- `settings.json`, `wiki/04-business-logic.md`, `wiki/05-settings-reference.md` — конфиг и
  документация
- `test/.../AnalogGroupResolverTest.kt` — тесты резолверов

Точка вызова — без нового `Status`/worker/pipeline-шага: `runAnalogGroupsMigration()` вызывается
напрямую из конца `runLinksMigration()`, т.к. `idLink`, нужный для `new-change-variant-2`,
существует только после того, как структурные связи реально созданы (`linkObjects(...)`),
а это происходит внутри того же шага "Связи". Конкурентность — построение групп идёт строго
последовательно по группам (не параллельно), тот же документированный deadlock Postgres при
конкурентных вызовах `new-change-group-2`, что и у групп замены материала.

## Инциденты, найденные при отладке на реальных данных

### 1. `EditObject/new-object` неприменим к ПОЛИНОМ-интегрированным типам

Fallback-объект изначально создавался обычным `NewObjectInputDto` (`EditObject/new-object`),
ключевой атрибут — из свойства "наименование" найденного элемента ПОЛИНОМ. Реальная ошибка
сервера:

```
500 Internal Server Error: "Метод NewObject неприменим для создания интегрированных с
ПОЛИНОМ:MDM объектов. Используйте метод NewBoObject."
```

`materials.materialTarget` ("Материал по КД") в этом экземпляре Loodsman настроен как
ПОЛИНОМ-интегрированный тип — создаётся только через `createBoObject`/location (тот же путь, что
`resolveOrCreateMaterial`/`resolveBomMaterialByClassifierCode` в `MaterialsEngine.kt`).
Обозначение при этом отдельно не задаётся — берётся автоматически из location-привязки к
найденному элементу ПОЛИНОМ. **Фикс:** `resolveOrCreateAnalogFallbackObject` переведён на
`createBoObject`.

### 2. Неверный тип fallback-объекта ("Деталь" вместо "Материал по КД")

Промежуточная версия настроек задавала `fallbackObjectTarget="Деталь"` — созданный объект получал
не тот тип, из-за чего группа замены (`groupType=2`, "материал") отображалась в Loodsman только с
одним вариантом. **Фикс:** отдельные `fallbackObjectTarget`/`fallbackObjectState` убраны из
настроек, fallback-объект всегда создаётся с типом/состоянием `mapping.materials.materialTarget`/
`materialState` — тем же, что у обычных материалов-заменителей.

### 3. Группа аналогов молча терялась при пересечении с потоком "Материалы по КД для DS"

Самый тонкий баг: пара родитель-потомок могла ОДНОВРЕМЕННО подходить и под условия потока
"Материалы по КД для DS" (родитель — DS-объект, потомок — строка раздела "Материалы"), и быть
частью группы аналогов. Веткование было написано как `if (DS-материал) ... else if (группа
аналогов) ...`, то есть ветки считались взаимоисключающими. При пересечении условий пара уходила
в поток DS, группа аналогов теряла этот вариант без единого сообщения в логе (поток DS для него
отрабатывал молча/штатно) — при этом объект создавался бы ЕЩЁ РАЗ отдельным вызовом
`createBoObject` на тот же location, что рисковало конфликтом по уникальному индексу. Диагностика
заняла несколько итераций: добавлены построчные логи чтения "группы аналогов" и попадания в
fallback, что и выявило — для проблемной строки была только строка "прочитана", но не было ни
"кандидат добавлен", ни "отложен на fallback". **Фикс:** порядок проверки инвертирован — группа
аналогов (более специфичный, явно указанный в данных сигнал) проверяется ПЕРВОЙ; поток DS —
только если группы аналогов нет.

### 4. Побочный фикс: дублирующиеся строки "Связи" могли затирать `analogGroup`

При разборе строк `classifierLinks[parentId][childId]` перезаписывался целиком каждой новой
строкой для той же пары (родитель, потомок) — если один и тот же потомок встречается в нескольких
строках листа "Связи" (дублирующиеся строки BOM), более поздняя строка без заполненной "группы
аналогов" могла затереть информацию, прочитанную из более ранней строки. Не подтвердилось как
основная причина инцидента №3, но исправлено как защитная мера: `analogGroup` больше не
перезаписывается на `null` последующей строкой — побеждает первое непустое значение.

## Диагностика, оставленная в коде

В `runLinksMigration()` (`MigrationEngine.kt`) оставлены построчные `println` при чтении "группы
аналогов" и при попадании потомка в fallback/happy-path — дёшево, полезно при разборе будущих
похожих инцидентов. Можно убрать по запросу.

## Верификация

Билд собирается (`./gradlew build` — проверено пользователем). Функциональность проверена на
реальном обменном файле: группа с fallback-объектом (потомок не в структуре, но есть в ПОЛИНОМ) и
основным вариантом (уже существующий объект, пересекавшийся с потоком DS) создаётся с обоими
вариантами корректно.
