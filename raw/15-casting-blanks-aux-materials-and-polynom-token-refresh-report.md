# Отчёт: литейные заготовки (связи), вспомогательные материалы для Детали, обновление токена ПОЛИНОМ

Итоговый отчёт по сессии из трёх связанных частей: (1) поток E — "Комплект вспомогательных
материалов" для произвольного объекта, читается из отдельного листа "Литейные заготовки связи";
(2) поток F — та же механика без ветвления по типу материала, для Детали, лист "Вспомогательные
материалы"; (3) инцидент на реальном прогоне — протухание `access_token` ПОЛИНОМ на длинной
миграции и его фикс. По ходу — два независимых бага, оба найдены на реальном прогоне пользователя.
Не входит в `wiki/index.md` — сырой отчёт для истории, актуальная выжимка перенесена в
`wiki/04-business-logic.md` (потоки E/F), `wiki/05-settings-reference.md`
(`mapping.castingBlanks`/`mapping.auxMaterials`), `wiki/03-external-api-quirks.md`,
`wiki/12-key-classes.md`, `wiki/14-known-issues.md`.

## Часть 1. Поток E: литейные заготовки — связи (`mapping.castingBlanks`)

### Что сделано

Новый независимый поток, в отличие от потоков A-D читает **свой отдельный лист Excel** ("Литейные
заготовки связи"), не "Объекты" и не "Связи" — архитектурно ближе к листу "Связи" (резолв родителя
по `classifierId` через уже собранный `identifiers`), чем к потоку D (там кандидаты собираются на
шаге "Объекты").

Столбцы: A — код классификатора родителя ("код объекта, к которому добавляем структуру"), B — код
классификатора входящего объекта (резолв в ПОЛИНОМ), плюс именованные — количество, единица,
"Цех-участок", "Тип материала".

1. Строки группируются по A. На первое встреченное значение A в группе создаётся ЛОЦМАН-объект
   "Комплект вспомогательных материалов" (`castingBlanks.setTarget`), обозначение = обозначение
   объекта-родителя, реверсивная связь `castingBlanks.setLinkType` ("Потребность для" — изначально
   было "Потребность в", пользователь поправил в ходе сессии) на родителя, субъект связи — комплект
   (тот же приём, что "Заготовка для" у потока D).
2. Ветвление по "Тип материала": `"Образец"` — не обрабатывается, лог; `"Основной"` — резолв в
   ПОЛИНОМ по коду B, тип `castingBlanks.materialTarget` ("Материал"); `"Вспомогательный"` — тот
   же резолв, тип `castingBlanks.auxMaterialTarget` ("Материал вспомогательный").
3. Материал линкуется к комплекту прямой связью `castingBlanks.materialLinkType` ("Состоит из
   ...", комплект — субъект).
4. На эту связь — норма расхода (`castingBlanks.rateAttribute`) и цех-потребитель
   (`castingBlanks.workshopAttribute`), оба — АТРИБУТЫ СВЯЗИ, `EditObject/up-link-attr-values` (см.
   часть 3 ниже про то, как цех-потребитель дошёл до этого состояния).

Родитель — объект ЛЮБОГО типа, созданный на шаге "Объекты" (обычная "Деталь", "Технологическая
деталь" и т.п.); в ходе сессии пользователь дважды уточнял назначение фичи ("Комплект" создаётся
для "Технологическая деталь", не для "Деталь") — оба раза не потребовалось менять код: резолв
родителя по `classifierId` изначально не проверяет тип объекта.

## Часть 2. Поток F: вспомогательные материалы для Детали (`mapping.auxMaterials`)

### Что сделано

Явно поставлено пользователем как "подобная функциональность только для Детали". Архитектурно
идентично потоку E, с двумя отличиями:

- источник — свой отдельный лист "Вспомогательные материалы";
- парсинг родителя/материала — **по имени столбца** ("Код классификатора ДСЕ", "Код классификатора
  материала"), а не по индексу буквы, как в потоке E — пользователь на этот раз дал только названия
  колонок, без букв;
- **без ветвления** по типу материала — всегда один тип, `auxMaterials.materialTarget` ("Материал
  вспомогательный").

Остальное — 1-в-1 с потоком E: "Кол-во" → норма расхода, "Ед.изм" → единица, "Цех-участок" →
цех-потребитель (оба — атрибуты связи "Состоит из ...").

Общая часть (создание комплекта + реверсивная связь на родителя) вынесена из
`CastingBlanksEngine.kt` в отдельный `migration/MaterialsKitEngine.kt`
(`createMaterialsKit(parent, setTarget, setState, setLinkType, ...)`), параметризованный голыми
строками вместо объекта настроек — единственный код, общий между потоками E и F.

## Часть 3. Инцидент: "Цех-потребитель" — атрибут объекта или связи?

История в трёх итерациях, поучительна тем, что почти дословно повторяет уже задокументированный
инцидент с "Нормой расхода" в потоке D (`raw/13-blanks-and-main-material-feature-report.md`,
раздел "Норма расхода не проставлялась — неверная модель данных") — тот прецедент не спас от
повторения ошибки, потому что вопрос был явно задан пользователю через `AskUserQuestion` и
пользователь на тот момент ответил "на объект".

1. **Первая реализация** — "Цех-потребитель" как атрибут ОБЪЕКТА материала
   (`EditObject/up-attr-values-by-ids`, по `versionId`) — по прямому ответу пользователя на
   `AskUserQuestion` на этапе планирования потока E ("куда ставить — на связь или на объект?" →
   "на объект"). Проверка результата (`isSuccess`) при этом изначально ОТСУТСТВОВАЛА — код слепо
   инкрементил счётчик "цехов назначено" независимо от ответа сервера. Баг найден и исправлен
   реактивно (добавлена проверка `isSuccess`/`errorMessage`, по образцу уже работающей проверки у
   нормы расхода), ДО того как стало известно про 410202 — то есть сначала был исправлен только
   "мы не видим ошибку", а не сама ошибка.
2. **Реальный прогон** после фикса проверки результата вскрыл саму ошибку:
   `Ошибка 410202: Атрибут не соответствует типу` — Loodsman отвечал так на КАЖДУЮ попытку
   поставить "Цех-потребитель" на объект материала. Также на этом прогоне поймана `23505:
   duplicate key value violates unique constraint "stlocks_pkey"` при том же
   `up-attr-values-by-ids` — материал дедуплицируется по элементу ПОЛИНОМ (несколько строк с
   одинаковым кодом B → один Loodsman-объект), конкурентные корутины писали атрибут на ОДИН и тот
   же `versionId` одновременно, Postgres падал на вставке строки блокировки версии.
3. **Промежуточный фикс** 23505 — `KeyedMutex<Int>` (`migration/KeyedMutex.kt`), сериализующий
   `up-attr-values-by-ids` по конкретному `materialId` (разные материалы остаются конкурентными).
   Технически корректен, но лечил симптом, не причину.
4. **Пользователь уточнил ключевую находку**: "Цех-потребитель" — атрибут СВЯЗИ "Состоит из ...",
   не объекта. Финальный фикс — цех-потребитель переведён на `EditObject/up-link-attr-values` по
   `linkId` связи комплект→материал, тем же способом, что уже работающая норма расхода. `410202`
   исчезает по построению (атрибут теперь пишется туда, где он реально заведён в схеме). `23505`
   исчезает тоже — `linkId` уникален на каждую строку-кандидат (в отличие от `materialId`, связь
   НЕ дедуплицируется), гонки на общий `versionId` больше нет. `KeyedMutex.kt` удалён как более не
   нужный — не осталось ни одного вызывающего кода.

Вывод, зафиксированный в `wiki/03-external-api-quirks.md`: ошибка Loodsman `410202 "Атрибут не
соответствует типу"` в общем случае означает, что атрибут в вызове привязан не к тому носителю
(объект vs связь) в схеме — при следующей похожей задаче стоит уточнять носитель атрибута ДО
реализации, а не полагаться на ответ, полученный без проверки в самом Loodsman.

## Часть 4. Инцидент: протухание `access_token` ПОЛИНОМ (600 секунд)

### Что произошло

На прогоне после части 1 пользователь поймал десятки `HTTP 401` от ПОЛИНОМ (`get-location` и
другие эндпоинты) — токен, судя по всему, протух посреди длинной миграции.

### Фикс

`migration/PolynomAuthRetry.kt`, функция `callPolynom { token -> ... }`: оборачивает один вызов,
ловит `ResponseException` со статусом `401`, обновляет токен через `PolynomLogin.updateToken`
(эндпоинт `api/v1/login/update-token` был написан заранее — задел на будущее — но ни разу не
вызывался до этой сессии), повторяет вызов РОВНО один раз с новым токеном. Конкурентные `401`
одновременно от нескольких корутин coalesced через новый `MigrationContext.polynomTokenMutex`:
под локом сверяется, не обновил ли токен уже кто-то другой, пока текущая корутина ждала — если да,
второй сетевой запрос на обновление не делается.

Обёрнуты ВСЕ 19 точек вызова `polynomClient.*` в движке (`MigrationEngine.kt` — 4,
`MaterialsEngine.kt` — 13, `AnalogGroupsEngine.kt` — 2) — не выборочно, поскольку протухание токена
не привязано к конкретному эндпоинту, первым после истечения 600 секунд может оказаться любой из
них.

На прогоне, где впервые пробовались потоки E и F вместе (часть 3), сообщений `401` от пользователя
уже не было — механизм отработал молча, что косвенно подтверждает фикс рабочим.

## Верификация

Билд самостоятельно не запускался — по правилам проекта ждём проверки пользователем. Поток E и
механизм обновления токена ПОЛИНОМ подтверждены реальным прогоном (объекты создались, `401` не
повторились). Финальная версия потока F и фикс цех-потребителя (атрибут связи вместо объекта) на
момент написания отчёта пользователем ещё не прогнаны повторно.
