# Руководство по файлу настройки `settings.json`

См. также: [архитектура процесса](03-architecture.md), [правила сопоставления данных](04-mapping.md).

Это практическое руководство для человека, который настраивает перенос под
конкретное изделие/предприятие, но не обязан разбираться в устройстве
инструмента изнутри. Задача файла `settings.json` — сказать инструменту: куда
подключаться, откуда брать файл спецификации, и по каким правилам строки
Excel превращаются в объекты, связи и атрибуты целевой системы.

Все примеры ниже — из реально работающей настройки. Числа/названия можно
менять под своё изделие, сама структура (какие слова в каких местах, какие
скобки) — нет.

## 1. Прежде чем редактировать: правила формата JSON

Файл `settings.json` — текстовый файл в формате JSON. Формат строгий, малейшая
опечатка (лишняя/пропущенная запятая, незакрытая кавычка) — и файл целиком не
читается. Пять правил, которых достаточно для правок:

1. **Каждое значение-текст — в двойных кавычках:** `"Деталь"`, `"обозначение"`.
   Числа и `true`/`false`/`null` — без кавычек: `50`, `true`, `null`.
2. **Пары "ключ: значение" разделяются запятой**, кроме последней пары в
   блоке `{...}` или последнего элемента в списке `[...]` — после них запятой
   быть НЕ должно.
   ```json
   { "url": "...", "dbName": "loodsman" }   // между парами — запятая, после последней — нет
   ```
3. **Фигурные скобки `{ }`** — один блок настроек (например, один блок
   подключения). **Квадратные скобки `[ ]`** — список из нескольких блоков
   или значений (например, список правил `types`, список атрибутов).
4. **Русские буквы и пробелы в именах столбцов Excel — это нормально и
   обязательно должны совпадать буква в букву** с заголовком столбца в файле
   Excel (включая регистр и пробелы). Опечатка в названии столбца — самая
   частая причина, почему правило "не срабатывает".
5. Перед сохранением файла полезно проверить его в любом бесплатном
   онлайн-валидаторе JSON (или в текстовом редакторе с подсветкой синтаксиса)
   — это находит пропущенные скобки/запятые за секунды, до запуска переноса.

## 2. Общая структура файла

```json
{
  "connection": { ... },   // подключение к целевой PLM-системе
  "polynom": { ... },      // подключение к справочнику материалов и классификаторов
  "mapping": { ... }       // всё, что касается самого переноса данных
}
```

Все три блока обязательны. Дальше — по порядку.

## 3. Блок `connection` — подключение к PLM-системе

```json
"connection": {
  "dbName": "loodsman",
  "remember": false,
  "url": "http://127.0.0.1:8076/api/v4/",
  "maxConcurrentRequests": 50
}
```

| Поле | Что это | Кто задаёт значение |
|---|---|---|
| `dbName` | Имя базы данных PLM-системы, с которой работаем | администратор PLM-системы |
| `remember` | Запоминать ли пароль между запусками | обычно `false`, из соображений безопасности |
| `url` | Адрес сервера PLM-системы | администратор PLM-системы/ИТ |
| `maxConcurrentRequests` | Сколько запросов инструмент может отправлять в PLM-систему одновременно | подбирается опытным путём; больше — быстрее перенос, но выше нагрузка на сервер |

## 4. Блок `polynom` — подключение к справочнику материалов

```json
"polynom": {
  "url": "http://127.0.0.1:5100/",
  "storageId": null,
  "moduleName": "",
  "clientType": 0,
  "maxConcurrentRequests": 5
}
```

| Поле | Что это |
|---|---|
| `url` | Адрес сервера справочника материалов и классификаторов |
| `storageId` | Обычно `null` — задаётся только если справочник просит явно указать конкретное хранилище |
| `moduleName`, `clientType` | Технические параметры авторизации, значение согласуется с администратором справочника при подключении, дальше не меняется |
| `maxConcurrentRequests` | Тот же смысл, что в блоке `connection`, но для справочника материалов — отдельный предел, потому что это отдельная система |

## 5. Блок `mapping.source` — откуда брать файл спецификации

```json
"source": {
  "type": "xlsx",
  "path": "C:\\Users\\han\\Desktop\\data.xlsx"
}
```

`type` всегда `"xlsx"` — других форматов сейчас не поддерживается. `path` —
полный путь к файлу спецификации на диске. **Важно:** в пути обратный слэш
`\` нужно писать ДВОЙНЫМ (`\\`) — так того требует формат JSON, одинарный
слэш в пути приведёт к ошибке чтения файла.

## 6. Листы "Объекты" и "Связи"

```json
"objectsSheet": {
  "name": "Объекты",
  "headersRowIndex": 1
},
"linksSheet": {
  "name": "Связи",
  "headersRowIndex": 1,
  "parentColumnIndex": 1,
  "childColumnIndex": 2,
  "linkType": "Состоит из ...",
  "quantityColumn": "конструкторское количество",
  "unitColumn": "единица измерения входящего элемента в ДСЕ",
  "unitExcludeValues": ["шт"],
  "commentColumn": "Комментарий",
  "commentAttribute": "Примечание"
}
```

| Поле | Что это |
|---|---|
| `name` | Точное название листа Excel (вкладки внизу файла) |
| `headersRowIndex` | Номер строки с заголовками столбцов, считая с 1 (если заголовки в первой строке листа — пишем `1`) |
| `parentColumnIndex`/`childColumnIndex` (только у "Связи") | Номер СТОЛБЦА (не строки!) с кодом родителя/потомка, считая с 1 = столбец A, 2 = столбец B и т.д. |
| `linkType` | Название связи в PLM-системе, которой соединяются родитель и потомок |
| `quantityColumn`/`unitColumn` | Название столбца с количеством и с обозначением единицы измерения. Пустая строка `""` — означает "этот столбец не используется" (для количества — тогда всегда подставляется 1) |
| `unitExcludeValues` | Список значений единицы измерения, которые никогда не нужно передавать в PLM-систему как есть (например `"шт"`, `"компл"`) — для них проставится значение по умолчанию |
| `commentColumn`/`commentAttribute` | Столбец с произвольным текстом (например "Комментарий") и название атрибута связи, куда его записать (например "Примечание") — проставляется на КАЖДУЮ создаваемую связь этого листа, без исключений по типу объекта. Пустая строка в любом из двух полей — атрибут не читается/не проставляется |

**На что обратить внимание:** у листа "Объекты" столбцы ищутся ПО НАЗВАНИЮ
(поэтому там нет полей вроде `parentColumnIndex`), а у листа "Связи" родитель
и потомок — ПО НОМЕРУ СТОЛБЦА. Это осознанная особенность — не путать при
настройке под новый файл.

## 7. `identifierColumn` — главный опознавательный столбец

```json
"identifierColumn": "код классификатора"
```

Название столбца на листе "Объекты", который однозначно определяет строку —
по нему потом ищутся связи родитель-потомок на листе "Связи" и признаки
"это позиция раздела Материалы", "это изделие со своей спецификацией" и т.п.
Один на весь файл, менять без крайней необходимости не стоит — от него
зависит вся остальная настройка.

## 8. `attributes` — общие атрибуты для всех типов объектов

```json
"attributes": [
  { "attrColumn": "наименование", "loodsmanAttr": "Наименование" },
  {
    "attrColumn": "Без чертежа",
    "loodsmanAttr": "Дополнение наименования",
    "replace": { "type": "any", "find": "any", "target": "БЧ" }
  }
]
```

Список соответствий "столбец Excel → атрибут в PLM-системе", применяется КО
ВСЕМ типам объектов сразу (кроме организационных папок — для них атрибуты не
проставляются вовсе).

| Поле | Что это |
|---|---|
| `attrColumn` | Название столбца Excel — источник значения |
| `loodsmanAttr` | Точное название атрибута в PLM-системе, куда это значение записать |
| `numeric` | `true` — значение считается числом (запятая в дробном числе автоматически заменяется на точку перед отправкой). Оставлять `false` для текстовых атрибутов (марка материала, ГОСТ и т.п.), где запятая может быть частью текста |
| `unit` | Фиксированное обозначение единицы измерения атрибута (например `"мм"`) — константа, не столбец Excel |
| `replace` | Необязательное преобразование значения перед записью, см. ниже |

**`replace` — как использовать.** Сейчас поддержан один практический вариант
— "если в столбце Excel есть ЛЮБОЕ непустое значение — записать в PLM-систему
не само это значение, а фиксированную метку":
```json
"replace": { "type": "any", "find": "any", "target": "БЧ" }
```
Это работает как флажок "признак присутствует": не важно, что именно написано
в столбце "Без чертежа" — если там что-то есть, атрибут "Дополнение
наименования" получит текст "БЧ".

## 9. `types` — правила создания объектов (самый большой и важный раздел)

Это список правил. Каждое правило отвечает на вопрос: *"если строка листа
"Объекты" удовлетворяет вот этим условиям — создать объект вот такого типа"*.
Инструмент проверяет строку по ВСЕМ правилам подряд — строка может подойти
сразу под несколько правил (тогда создаётся несколько объектов, см.
[правила сопоставления, раздел 1](04-mapping.md#1-определение-типа-объекта)).

### 9.1. Каркас одного правила

```json
{
  "target": "Деталь",
  "source": "обозначение",
  "state": "Проектирование",
  "isProject": false,
  "isFolder": false,
  "linkToRoot": false,
  "conditions": { "single": {}, "or": [], "and": [ ... ] },
  "attributes": [ ... ]
}
```

| Поле | Что это | Значение по умолчанию, если не указано |
|---|---|---|
| `target` | Тип создаваемого объекта — точное название типа, как оно заведено в PLM-системе | обязательно |
| `source` | Название столбца, откуда берётся обозначение (ключевое имя) создаваемого объекта | обязательно |
| `state` | Состояние (статус) объекта при создании, точное название, как в PLM-системе | не указывается, если ниже задано `resolveViaPolynom: true` |
| `isProject` | Пометить объект как объект верхнего уровня ("проект"). Используется ТОЛЬКО для самого корня переноса, для обычных правил — не трогать, оставить `false` | `false` |
| `isFolder` | `true` — правило создаёт организационную папку (не входит в состав изделия, не получает атрибутов) | `false` |
| `linkToRoot` | `true` — объект жёстко привязывается к корню переноса, а не к папке/структуре | `false` |
| `conditions` | Условия отбора строк, см. ниже | обязательно |
| `attributes` | Атрибуты, специфичные ТОЛЬКО для этого правила — в дополнение к общему списку `mapping.attributes` (раздел 8) | список пустой |

### 9.2. `conditions` — как задать условие отбора строки

```json
"conditions": {
  "single": { "type": "check", "column": "Раздел спецификации", "is": "Изделия" },
  "or": [],
  "and": []
}
```

Три независимых группы условий, ВСЕ непустые группы должны выполниться
одновременно (между группами — логика "И"):

- **`single`** — одно условие. Если группа не нужна — оставить `{}`.
- **`or`** — список условий, из которых достаточно ХОТЯ БЫ ОДНОГО. Если группа
  не нужна — оставить `[]`.
- **`and`** — список условий, которые должны выполниться ВСЕ. Если группа не
  нужна — оставить `[]`.

Пустая группа (`{}` или `[]`) не блокирует правило — считается пройденной.
Можно использовать любую комбинацию из трёх групп сразу, если нужна сложная
логика (пример — правило "Деталь" ниже использует `and` из пяти условий).

**Одно условие** выглядит так:

```json
{ "type": "check", "column": "Раздел спецификации", "is": "Детали" }
```

| Поле | Что это |
|---|---|
| `type` | Вид проверки (см. таблицу ниже) |
| `column` | Название столбца Excel, который проверяем |
| `is` | Значение для сравнения (не нужно для проверки `"empty"`) |

Доступные виды проверки (`type`):

| `type` | Проверяет |
|---|---|
| `check` | Значение в столбце ТОЧНО РАВНО `is` |
| `notEndsWith` | Значение НЕ заканчивается на `is` |
| `endsWith` | Значение заканчивается на `is` |
| `empty` | Столбец пуст (значение `is` не указывается) |

### 9.3. Примеры реальных правил из рабочей настройки

**Организационная папка** (не входит в состав, атрибуты не проставляются):
```json
{
  "target": "Папка",
  "source": "обозначение",
  "state": "Папка для чтения",
  "isFolder": true,
  "linkToRoot": true,
  "conditions": {
    "single": { "type": "check", "column": "Раздел спецификации", "is": "Изделия" },
    "or": [], "and": []
  }
}
```

**Сборочная единица** (срабатывает по ЛЮБОМУ из двух значений раздела
спецификации — используется группа `or`):
```json
{
  "target": "Сборочная единица",
  "source": "обозначение",
  "state": "Проектирование",
  "conditions": {
    "single": {},
    "or": [
      { "type": "check", "column": "Раздел спецификации", "is": "Изделия" },
      { "type": "check", "column": "Раздел спецификации", "is": "Сборочные единицы" }
    ],
    "and": []
  }
}
```

**Деталь** (срабатывает, только если выполнены ВСЕ пять условий сразу —
группа `and`, включая двойную проверку на "не заканчивается на Т/T" — файлы
Excel иногда содержат и русскую, и латинскую букву Т):
```json
{
  "target": "Деталь",
  "source": "обозначение",
  "state": "Проектирование",
  "conditions": {
    "single": {},
    "or": [],
    "and": [
      { "type": "check", "column": "Тип АСУП", "is": "дет" },
      { "type": "check", "column": "Раздел спецификации", "is": "Детали" },
      { "type": "notEndsWith", "column": "обозначение", "is": "Т" },
      { "type": "notEndsWith", "column": "обозначение", "is": "T" },
      { "type": "empty", "column": "Тип объекта" }
    ]
  },
  "attributes": [
    { "attrColumn": "Масса детали", "loodsmanAttr": "Масса", "numeric": true }
  ]
}
```

**Технологическая деталь** (особый случай — связь с этим объектом в составе
изделия строится в обратную сторону, поля `childLinkType`/
`childOfSameTypeLinkType`, см. [правила сопоставления](04-mapping.md#1-определение-типа-объекта)):
```json
{
  "target": "Технологическая деталь",
  "source": "обозначение",
  "state": "Проектирование",
  "childLinkType": "Технологическая ДСЕ для",
  "childOfSameTypeLinkType": "Изготавливается из ...",
  "conditions": {
    "single": {},
    "or": [
      { "type": "endsWith", "column": "обозначение", "is": "Т" },
      { "type": "endsWith", "column": "обозначение", "is": "T" }
    ],
    "and": [
      { "type": "check", "column": "Раздел спецификации", "is": "Детали" },
      { "type": "check", "column": "Тип АСУП", "is": "дет" },
      { "type": "empty", "column": "Тип объекта" }
    ]
  }
}
```
Не трогайте `childLinkType`/`childOfSameTypeLinkType`, если не уверены — их
значения жёстко привязаны к тому, как в PLM-системе настроены типы связей;
неверное значение здесь приводит к ошибке при создании связи, а не к тихому
пропуску.

**Стандартное/Прочее изделие** (объект не создаётся напрямую, а находится в
справочнике материалов по коду классификатора — поле `resolveViaPolynom`;
обратите внимание, что `state` здесь НЕ указывается вовсе — состояние
назначает сама PLM-система):
```json
{
  "target": "Стандартное изделие",
  "source": "обозначение",
  "resolveViaPolynom": true,
  "conditions": {
    "single": {},
    "or": [],
    "and": [
      { "type": "check", "column": "Раздел спецификации", "is": "Стандартные изделия" },
      { "type": "check", "column": "Тип АСУП", "is": "дет" },
      { "type": "empty", "column": "Тип объекта" }
    ]
  }
}
```

### 9.4. Чек-лист: как добавить новый тип объекта

1. Определить, какой раздел/признак в Excel однозначно отличает нужные
   строки от остальных (один столбец или комбинация нескольких).
2. Скопировать структуру ближайшего похожего правила (например, "Деталь" —
   для обычного объекта, "Стандартное изделие" — если объект должен
   находиться через справочник материалов).
3. Проверить точное название целевого типа объекта и состояния — оно должно
   СОВПАДАТЬ буква в букву с тем, что заведено в PLM-системе (регистр, точки,
   многоточия — как в примерах выше, например `"Состоит из ..."` с
   многоточием, а не тремя точками подряд без пробела).
4. Добавить блок правила в список `types` (не забыть запятую после
   предыдущего правила в списке).
5. Проверить файл валидатором JSON перед запуском (см. раздел 1, пункт 5).

## 10. `materials` — материалы по чертежу и заменители

```json
"materials": {
  "appliesToTargets": ["Деталь"],
  "drawingDesignationColumn": "Обозначение материала по чертежу",
  "substituteDrawingDesignationColumn": "Материал заменитель по чертежу",
  "classifierCodeColumn": "Код классификатора объекта который записан в поле сортамента",
  "classifierCodePropertyAbsoluteCode": "c:ClassifData::pd:ClassifCode",
  "codesReferenceName": "Коды",
  "materialTarget": "Материал по КД",
  "detailLinkType": "Изготавливается из ...",
  "hierarchy": {
    "referenceName": "Конструкторские материалы",
    "catalogName": "Материалы по КД",
    "groupName": "Обозначение материала по чертежу"
  },
  "changeGroupName": "Замена материала",
  "mainMaterialVariantName": "Основной материал",
  "substituteMaterialVariantName": "Материал-заменитель",
  "attributes": [
    { "attrColumn": "Марка", "loodsmanAttr": "Марка материала" },
    { "attrColumn": "ГОСТ", "loodsmanAttr": "НТД на материал" }
  ]
}
```

| Поле | Что это |
|---|---|
| `appliesToTargets` | К каким типам объектов (из раздела `types`) применяется поиск материала — обычно `["Деталь"]` |
| `drawingDesignationColumn` | Столбец с обозначением материала по чертежу (основной материал) |
| `substituteDrawingDesignationColumn` | Столбец с обозначением материала-заменителя. Пустая строка `""` — заменители не ищутся вовсе |
| `classifierCodeColumn` | Столбец с кодом классификатора материала (не путать с `identifierColumn` из раздела 7 — это код самого МАТЕРИАЛА, не объекта) |
| `classifierCodePropertyAbsoluteCode`, `codesReferenceName` | Технические координаты поиска в справочнике материалов — задаются один раз при подключении к конкретному справочнику, администратором справочника, дальше не меняются |
| `materialTarget` | Тип создаваемого объекта материала в PLM-системе |
| `detailLinkType` | Название связи между деталью и материалом |
| `hierarchy` | Куда в справочнике материалов помещать новый материал, если поиск по коду не дал результата (раздел → каталог → группа) — все три должны заранее существовать в справочнике |
| `changeGroupName`, `mainMaterialVariantName`, `substituteMaterialVariantName` | Названия, под которыми в PLM-системе появится группа замены материала и её два варианта |
| `attributes` | Атрибуты объекта материала — та же структура, что в разделе 8 |

## 11. `analogGroups` — группы аналогов

```json
"analogGroups": {
  "analogGroupColumn": "группа аналогов",
  "productionQuantityColumn": "производственное количество",
  "productionQuantityWithoutMergeColumn": "количество производственное без объединения",
  "changeGroupNameTemplate": "Группа аналогов {group}",
  "variantNameTemplate": "Вариант {variant}"
}
```

`analogGroupColumn` — столбец листа "Связи" с меткой вида `"1-2"` (первое
число — номер группы аналогов у родителя, второе — номер варианта внутри
неё). Пустая строка `""` в этом поле выключает всю функцию группы аналогов.
`changeGroupNameTemplate`/`variantNameTemplate` — шаблоны названий, `{group}`
и `{variant}` автоматически заменяются на конкретные номера.

## 12. `bomMaterials` — материалы по КД для изделий со своей спецификацией

```json
"bomMaterials": {
  "specificationConditions": {
    "single": { "type": "check", "column": "конструкторская спецификация", "is": "DS" },
    "or": [], "and": []
  },
  "materialConditions": {
    "single": { "type": "check", "column": "Раздел спецификации", "is": "Материалы" },
    "or": [], "and": []
  }
}
```

`specificationConditions` — условие, по которому объект считается "имеющим
собственную спецификацию" (в примере — значение `"DS"` в столбце
"конструкторская спецификация"). **Если этот блок вообще не заполнен — вся
функция выключена целиком.** `materialConditions` — как распознать строку
раздела "Материалы" на листе "Объекты" (если не заполнено — считается, что
подходит любая строка, это доп. фильтр поверх `specificationConditions`).
Формат условий — тот же `Conditions`, что в разделе 9.2.

## 13. `blanks` — заготовки и материал основной

```json
"blanks": {
  "target": "Заготовка",
  "state": "Проектирование",
  "linkType": "Заготовка для",
  "materialTarget": "Материал основной",
  "materialLinkType": "Изготавливается из ...",
  "rateColumn": "Норма расхода",
  "rateUnitColumn": "Единица измерения",
  "rateAttribute": "Норма расхода",
  "appliesToTargets": ["Деталь", "Технологическая деталь"],
  "attributes": [ ... ],
  "materialAttributes": [ ... ]
}
```

| Поле | Что это |
|---|---|
| `target` | Тип создаваемой заготовки. **Пустая строка `""` выключает весь этот блок функциональности целиком** |
| `state` | Состояние заготовки при создании |
| `linkType` | Название связи деталь↔заготовка (связь направлена от заготовки к детали — это заложено в самой PLM-системе, в настройке ничего разворачивать не нужно) |
| `materialTarget`/`materialLinkType` | Тип объекта "материал основной" заготовки и название связи заготовка→материал |
| `rateColumn`/`rateUnitColumn`/`rateAttribute` | Столбцы со значением и единицей нормы расхода + название атрибута связи, куда её записать. Пустые значения — норма расхода не читается/не проставляется, остальное работает как обычно |
| `appliesToTargets` | Для каких типов объектов (из раздела `types`) собираются заготовки — свой список, независимый от `materials.appliesToTargets` (раздел 10) |
| `attributes` | Атрибуты САМОЙ заготовки (диаметр, длина и т.п.) |
| `materialAttributes` | Атрибуты СВЯЗИ заготовка→материал (например, конкретный профиль отреза) — используйте это, а не атрибут объекта материала, если значение может отличаться между разными заготовками с общим материалом (подробное объяснение — [правила сопоставления, раздел 5](04-mapping.md#5-заготовки-и-основной-материал-заготовки)) |

## 14. `castingBlanks` — литейные заготовки (свой лист Excel)

```json
"castingBlanks": {
  "name": "Литейные заготовки связи",
  "headersRowIndex": 1,
  "parentColumnIndex": 1,
  "childColumnIndex": 2,
  "quantityColumn": "количество материала в литейной заготовке",
  "unitColumn": "Ед. изм.",
  "workshopColumn": "Цех-участок",
  "materialTypeColumn": "Тип материала",
  "setTarget": "Комплект вспомогательных материалов",
  "setState": "Проектирование",
  "setLinkType": "Потребность для",
  "materialTarget": "Материал",
  "auxMaterialTarget": "Материал вспомогательный",
  "materialLinkType": "Состоит из ...",
  "rateAttribute": "Норма расхода",
  "workshopAttribute": "Цех-потребитель"
}
```

Читает ОТДЕЛЬНЫЙ лист Excel (`name`), не "Объекты" и не "Связи".
`parentColumnIndex`/`childColumnIndex` — номера столбцов (как в разделе 6, по
номеру, не по названию). `materialTypeColumn` — столбец со значением
`"Образец"` / `"Основной"` / `"Вспомогательный"` (сами эти три слова в коде
зафиксированы, менять в настройке нельзя — можно только менять НАЗВАНИЕ
столбца, где они ищутся). `setTarget` пустой — выключает весь блок целиком.

  "headersRowIndex": 1,
  "parentColumn": "Код классификатора ДСЕ",
  "childColumn": "Код классификатора материала",
  "quantityColumn": "Кол-во",
  "unitColumn": "Ед.изм",
  "workshopColumn": "Цех-участок",

## 16. Частые ошибки при настройке

| Симптом | Вероятная причина |
|---|---|
| Правило "не срабатывает", объект не создаётся | Название столбца в `column`/`attrColumn` не совпадает буква в букву с заголовком в Excel (лишний пробел, другой регистр, "ё" вместо "е") |
| Файл не запускается, ошибка чтения настройки | Нарушен синтаксис JSON — пропущена/лишняя запятая, незакрытая скобка или кавычка (см. раздел 1) |
| Объект создаётся, но не туда/не с тем типом связи | Перепутаны `childLinkType`/`childOfSameTypeLinkType` — направление связи в PLM-системе заведено в одну конкретную сторону, значение поля должно ей соответствовать |
| Атрибут не проставляется, хотя столбец заполнен | Числовое значение с запятой при `numeric` не указан `true` — либо наоборот, `numeric: true` стоит на текстовом столбце и там встречаются нечисловые значения |
| Материал/заготовка/группа не создаются вовсе | Соответствующий блок (`blanks.target`, `castingBlanks.setTarget`, `auxMaterials.setTarget`, `analogGroups.analogGroupColumn`, `bomMaterials.specificationConditions`) оставлен пустым — это штатный способ выключить функцию целиком, полезно проверить, не выключен ли он случайно |
| Слэши в пути к файлу вызывают ошибку | В пути `mapping.source.path` каждый обратный слэш `\` должен быть удвоен: `\\` |

## 17. Порядок действий при настройке под новое изделие/предприятие

1. Уточнить у ИТ/администратора PLM-системы адрес, имя базы, точные названия
   типов объектов и связей, которые заведены в системе (раздел 3, 9.3).
2. Уточнить у администратора справочника материалов координаты подключения и
   название разделов справочника (раздел 4, 10).
3. Сверить состав и точные названия столбцов реального файла спецификации
   заказчика с примерами в разделах 6–15.
4. Настроить правила `types` по образцу раздела 9, начиная с самых простых
   (папка, деталь) — проверять по одному правилу, не переписывать всё сразу.
5. При необходимости включить дополнительные блоки (материалы, заготовки,
   литейные заготовки, вспомогательные материалы, группы аналогов) — каждый
   независим и может быть включён/выключен отдельно (см. таблицу в разделе
   16, строка про пустые значения).
6. Проверить файл валидатором JSON, запустить перенос на небольшом тестовом
   файле спецификации перед боевым запуском на полном объёме данных.
